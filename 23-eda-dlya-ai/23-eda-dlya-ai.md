## TL;DR

EDA — это инверсия контроля: продюсер публикует **факт** в брокер и не знает, кто его слушает; потребители масштабируются независимо, а буфер брокера сглаживает пики. Для AI мотив прямой: инференс тяжёлой модели занимает сотни миллисекунд, и блокировать на это клиентский запрос дорого и рискованно. Цена — распределённая система со всеми её проблемами: доставка **at least once** требует **идемпотентности**, порядок гарантируется только внутри партиции (нужен осмысленный **ключ партицирования**), а бизнес-процесс перестаёт читаться по коду одного сервиса. Ключевой выбор в дизайне событий — **Domain Events** (`FraudScoreExceeded`, `AccountBlocked` — несут намерение) против **Data-Centric/CDC** (`UserUpdated` — дёшевы, но потребитель вынужден считать diff), и **Fat vs Thin Event**: лектор прямо рекомендует **Fat** — автономность потребителя важнее размера сообщения, потому что Thin Event превращает каждое событие в поход в БД. **Event Sourcing** (хранить события, а не состояние) даёт бесплатный аудит-лог и темпоральные запросы — для AI это основа **Explainable AI**: можно восстановить, на каких данных модель приняла решение; **CQRS** чинит его главный минус — сложность выборок. Разделение инструментов: **Kafka** — транспорт и маршрутизация (retention, offsets, нет индексов), **Event Store** — source of truth для аудита. Для AI отдельно разобраны: **streaming-агрегация фич** и риск **training-serving skew**, **триггерное переобучение** (Data Drift / Concept Drift / Labels Arrived) вместо cron, и три топологии инференса — embedded, external service, fully async. Финальный кейс — fraud monitoring на 10 000 TPS с бюджетом < 200 мс, где чистый EDA проигрывает: выбран **sidecar** — Flink + ML-модель в одном поде, gRPC over Unix Domain Socket, агрегаты в локальной RocksDB, шардирование по `User_ID`.

## Контекст и проблема

Синхронная интеграция закладывает две связности сразу: **адресную** (продюсер обязан знать API потребителя) и **временну́ю** (оба сервиса должны быть живы одновременно). Для AI это ломается быстрее, чем для CRUD: инференс BERT/LLM — сотни миллисекунд, и синхронная цепочка либо держит клиента, либо рвётся по таймауту. Отсюда переход «от запросов к потокам событий» — но переход не бесплатный, и вторая половина лекции честно про то, чем за него платят.

## Ключевые тезисы

### Смена парадигмы: почему синхронность убивает масштабируемость

- **Связность:** в синхронной системе продюсер обязан знать адрес и API потребителя. **Временна́я связность:** оба сервиса должны быть доступны одновременно.
- **Проблема для AI:** инференс тяжёлых моделей (BERT, LLM) занимает время — блокировать клиентский запрос на 500 мс+ дорого и рискованно.
- **EDA** — архитектурный шаблон из несвязанных сервисов, которые публикуют, потребляют или маршрутизируют события; продюсер публикует событие в **брокер**, потребители его обрабатывают. Это распределённая система: компоненты на разных серверах, взаимодействие по сети.
- **Преимущества:** слабая связанность (брокер — посредник), горизонтальное масштабирование продюсеров и потребителей независимо, отказоустойчивость (не подтверждённое событие не теряется — его переобработает другой экземпляр или тот же сервис после восстановления).
- **Проблемы:** (1) **понимание бизнес-процесса** — по исходникам одного сервиса не видно, как реализован процесс целиком; (2) **проектирование под отказ** — ненадёжная сеть требует корректной обработки повторов (**идемпотентность**) и сообщений не по порядку (**коммутативность**).

### Событие, команда, запрос

- **Событие (Event)** — «факт», сообщение о произошедшем изменении состояния; требования к другому сервису нет (`ProductAdded`, `OrderCreated`).
- **Команда (Command)** — «глагол», требование что-то сделать, ожидается реакция конкретного получателя (`AddProduct`, `CreateOrder`).
- **Запрос (Query)** — получение состояния без его изменения (`getProduct`, GET-запрос).

### Что внутри события: Thin vs Fat

- Форматы: JSON, XML, Protobuf, Thrift, Avro.
- **Thin Event** — только ID, получатель сам идёт в БД за данными. Минус: нагрузка на БД (и сетевой round-trip на каждое событие).
- **Fat Event** — либо конкретные изменения (specific changes), либо снимок всей записи (snapshot). Плюс — автономность потребителя, минус — размер сообщения.
- В итоговых тезисах лектор занимает сторону: **выбирайте Fat Events**, чтобы снизить нагрузку на БД и повысить автономность сервисов.

### Pub/Sub, DLQ и выбор брокера

- **Издатель-подписчик:** один издатель — много подписчиков, издатель не знает слушателей. Новый AI-сервис («анализ тональности») добавляется подпиской на тот же топик, без правки кода загрузчика файлов. Отличие от очереди: в очереди сообщение читает **один** консьюмер, в Pub/Sub копию получают **все** активные подписчики.
- **Dead Letter Queue:** сообщение, роняющее парсер или модель (битый PDF, атака на модель), без DLQ крутится в бесконечном цикле и забивает ресурсы. Решение — после N попыток изолировать в DLQ для ручного разбора.
- **RabbitMQ vs Kafka:** RabbitMQ — очередь задач («smart broker»), сообщение удаляется после ack, средняя производительность и сложность, AI-кейс — **inference queue** (распределение задач на воркеры). Kafka — лог событий («dumb broker»), хранение N дней с возможностью **replay**, высокая сложность и очень высокая производительность, AI-кейс — **training data / logs** (сбор данных для обучения).

### Гарантии доставки и порядок

- Брокеры по умолчанию дают **at least once**: без подтверждения событие отправляется повторно → **обработка обязана быть идемпотентной** (дедупликация по идентификатору события).
- Правильный порядок нужно сначала **определить**, а потом обеспечить: брокеру нужен **ключ**, по которому определяется секция (партиция) с FIFO. Пример со слайда: события `OrderCreated` / `ProductAdded` / `OrderCancelled` с ключом агрегата `101` обязаны лежать в одной партиции — иначе отмена может обогнать создание.
- **Saga:** **оркестрация (DAG)** — оркестратор говорит участникам, какие локальные транзакции выполнять; **хореография (EDA)** — каждая локальная транзакция публикует доменные события, запускающие транзакции в других сервисах (ссылка на microservices.io/patterns/data/saga.html).

### Проектирование событий: Domain vs Data-Centric

- **Data-Centric events** — события изменения сущностей в БД (`OrderCreated`, `OrderUpdated`); реализуются через **CDC**, просты в генерации, но **теряют бизнес-контекст** — потребитель вынужден вычислять diff состояний.
- **Domain Events** — факты предметной области (`OrderSubmitted`, `FraudScoreExceeded`, `AccountBlocked`); несут явную семантику и намерение, но требуют аналитики и осознанного проектирования на стороне источника.
- Живой пример неоднозначности: пользователь сменил статус `active` → `blocked`. Какое событие — `UserUpdated`, `UserBlocked`, `UserStatusChanged` или все сразу? Что в payload — только изменение, новое состояние целиком или только id? Блокировка пользователя блокирует все его кампании и баннеры — одно событие или по одному на объект? **Однозначного ответа нет** — ровно как нет его для REST (`PATCH /users/{id}` vs `POST /users/{id}/block` vs `POST /users/update`).
- С чего начинать: от **предметной области**, с основного пользовательского сценария, связывая каждое событие с доменом и **не думая на первых итерациях о реализации на бэкенде**. Domain Events как часть DDD — карта bounded contexts (Order Entry, Order Management, Invoicing, Billing, Stock, Catalog, Loyalty) с событиями на границах.

### Event Sourcing и CQRS

- **Event Sourcing** — в БД хранятся **только события**, а не состояние объекта. Плюсы: бесплатный аудит-лог; хорошая производительность event-store; **темпоральные запросы** (состояние на момент времени); любая аналитика, поскольку хранится всё. Минусы: тяжёлые миграции данных; резкий рост объёмов и падение производительности (лечится **снапшотами**); сложные выборки (лечится **CQRS**).
- **CQRS** — разделение моделей данных для модификации и для чтения: транзакции пишутся в свою таблицу, а Balance Service строит из событий (`InvoiceGenerated`, `InvoicePaid`) отдельную read-модель с балансом.
- **Log-based брокер vs Event Store:** Kafka — транспорт, буферизация, последовательное массовое чтение, ограниченный retention, чтение по offsets, **нет индексов** → нельзя эффективно искать историю одного агрегата. Event Store — БД для Event Sourcing: независимые streams по сущностям, оптимистичная блокировка, нативные проекции и чтение истории конкретного объекта. **Стратегия:** Kafka для высоконагруженной маршрутизации, Event Store — «золотой источник» для аудита и **Explainable AI**.

### EDA и AI

- **Real-time feature engineering.** Батч убивает актуальность: агрегаты, посчитанные раз в ночь, не увидят атаку, начавшуюся 5 минут назад. Решение — **streaming aggregation** оконными функциями (`count(transactions) over (partition by user_id range interval '1 hour')`). **State Layer работает как feature store**, наполняемый в реальном времени (на схеме: Kafka → Stream Processor (Flink/Spark) → Online Store (Redis) + Offline Store (ClickHouse) → Serving/Training). Главный риск — **training-serving skew**: логика расчёта фич в стриминге (Java/Scala) расходится с аналитикой (Python/Pandas), между Online и Offline Store нужен **consistency check** по схеме и логике.
- **Реактивное переобучение.** Static (cron «переобучать каждое воскресенье») неэффективен, если данные не менялись, и опасен, если появился новый тип мошенничества. Dynamic — запуск пайплайна по **событию-триггеру**: `Data Drift Detected` (распределение входных данных изменилось), `Concept Drift Detected` (accuracy/F1 на свежих данных ниже порога), `Labels Arrived` (накоплено N новых размеченных примеров). Отдельно: **ground truth приходит с задержкой** (клиент оспорил транзакцию через 2 дня) — это тоже событие (`LabelDelayed`), которое должно попасть в Store.
- **Топология inference pipeline.** (1) **Embedded model** — ONNX/POJO прямо в памяти consumer-сервиса: нулевой сетевой оверхед и максимальный throughput, но не масштабируется отдельно, обновление требует редеплоя, конфликт за CPU/RAM. (2) **External model service (RPC/sidecar)** — consumer собирает фичи и делает gRPC/REST-вызов: чистое разделение ответственности и независимый скейлинг GPU-подов, но сетевые задержки и риск синхронной блокировки обработки очереди. (3) **Asynchronous inference (fully EDA)** — на слайде только заголовок, раскрывался голосом.

### Кейс: real-time fraud monitoring

- **Требования:** блокировать подозрительные операции **до списания**; **latency строго < 200 мс** на весь цикл (при просрочке валидации транзакция уходит на постобработку); **10 000 TPS** в пике. **Ограничение:** модели нужен контекст — предрассчитанные агрегаты за 30 дней (средний чек, география); «сырая» транзакция без них бесполезна.
- **Анализ альтернатив.** Вариант А, **чистый EDA (async)**: две записи в Kafka + два чтения + время на репликацию; при падении модели сообщение лежит в Kafka, нужны DLQ и процесс разбора; зато независимые сервисы — модель обновляется, Flink продолжает работать. Вариант Б, **sidecar/direct (sync)**: данные идут через RAM (Unix socket), колебания задержки минимальны, доступны и Kafka (near-online), и gRPC (online); ошибка вызова → Flink сразу применяет **fallback** («пропустить по лимитам»); минус — единый под, обновление модели требует рестарта Flink и сложный resource management.
- **Архитектурные решения** (требование → проблема → решение): строгий порядок событий → в распределённой системе порядок нарушается → **`User_ID` как partition key**; latency < 200 мс → ходить в PostgreSQL за историей на каждой транзакции = DDoS собственной базы → **шардированные агрегаты клиента прямо на диске/в памяти воркера** stream processor'а + маршрутизация gRPC-трафика перед подами; latency < 200 мс → инфраструктура на JVM, а модели пишут на Python → **паттерн sidecar**: Java и Python в одном поде, общение через **gRPC over Unix Domain Socket**.
- **Итоговая топология:** Smart gRPC Gateway (L7 consistent hashing, роутинг в под по `User_ID`) → Kubernetes Pod (stateful worker/shard): Processing Unit (Flink/Java) — enrichment из **локальной RocksDB** (шард агрегатов, восстанавливается из offline store) → scoring через **ML Sidecar** (gRPC over UDS) → decision; async-логи фич и решений уходят в Kafka (`features-ready`, `fraud-decisions`), сырые транзакции читаются из Kafka, партицированные по `User_ID`. Данные не покидают оперативную память сервера (loopback) — «скорость почти как у прямого вызова функции при полной изоляции процессов».

## Вопросы и ответы

Вопросы для самопроверки со слайда 57:

1. **Как Event Sourcing помогает в задачах Explainable AI?** — Полный журнал фактов позволяет воспроизвести состояние на момент решения модели: какие фичи и какая версия модели дали именно этот скор.
