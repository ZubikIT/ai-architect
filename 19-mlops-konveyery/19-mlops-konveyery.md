## TL;DR

**MLOps ≠ DevOps: добавляется третье измерение — данные и качество модели.** DevOps-артефакт «либо работает, либо нет»; ML-сервис может «работать» технически, но деградировать из-за data drift — это надо отслеживать отдельно. Отсюда: версионирование датасетов, feature stores, мониторинг метрик модели, переобучение по расписанию. **MLOps-конвейер** — автоматизированная цепочка (1) сбор данных → (2) обучение → (3) валидация → (4) деплой → (5) мониторинг, запускаемая без ручного вмешательства.

**Три инструмента стека:** **Airflow** — оркестрация (DAG на Python, расписание, retry-логика; «контролирует выполнение, но не знает ничего про ML»; минусы — нет нативной поддержки ML-артефактов, требует DevOps-настройки); **MLflow** — «память системы» (логирует параметры/метрики/артефакты, Model Registry со Staging → Production, полная lineage каждой модели); **Kubeflow** — масштабирование (ML-платформа на K8s, нативные эксперименты и GPU/TPU; минусы — жёсткая привязка к K8s, высокий порог входа).

**Пайплайн переобучения (эталон со слайда):** Триггер (расписание или дрейф) → Загрузка данных (feature store, N дней) → Обучение (новая версия + MLflow) → Автовалидация (accuracy/F1/AUC; не в норме → алерт, пайплайн остановлен) → Сравнение с prod (новая vs текущая; хуже → уведомление, версия отклонена) → Деплой (Blue-Green — две полные среды, мгновенное переключение и откат / Canary — 5%→25%→100% с контролем метрик на каждом шаге) → Мониторинг. Триггеры переобучения: **по времени** (еженедельно при стабильных данных, ежедневно в быстро меняющейся среде, по числу новых сэмплов) и **по качеству** (метрики ниже порога, data drift > threshold, жалобы/аномалии).

**Model drift** — деградация качества в проде из-за того, что реальные данные перестают соответствовать обучающим. **Data drift**: изменилось распределение входов X (другой регион, другой портрет пользователя). **Concept drift**: изменилась связь X→Y (поведение изменилось из-за внешних событий). Обнаружение: статистические тесты (KS-test, **PSI**, Chi-square — train vs prod), **Evidently AI** (готовые отчёты, интегрируется с Airflow), Prometheus + Grafana (latency, prediction distribution, feature stats), алертинг + автоответ (почта/PagerDuty + автозапуск retrain-DAG). Кейс: рекомендательный сервис после праздников, PSI > 0.2 → Evidently фиксирует и генерит JSON-отчёт → Grafana-алерт → Airflow автоматически запускает retrain на данных последних 30 дней → после валидации canary-деплой.

**Практика — MLOps-пайплайн для RAG** (документы еженедельно обновляются в S3; нужно автоматически пересчитывать эмбеддинги и обновлять векторную БД): триггер — новый документ в S3 (S3KeySensor) или cron → Airflow DAG: загрузка документов → chunking (512–1024 токена) + embedding (батчами — экономия API-вызовов) → upsert в Qdrant/Chroma/FAISS → smoke-test (5–10 тестовых запросов проверяют релевантность **до** переключения) → версионирование снапшота базы (каждый rebuild = новая версия с датой). Мониторинг: retrieval latency (avg + P99), hit rate (доля запросов с similarity > 0.75), user feedback (лайк/дизлайк); авто-триггер при hit rate < 0.6 или N+ новых документов; **rollback к предыдущей версии базы при падении метрик**. Расширенный мониторинг — Deepeval (precision/recall/F1, contextual precision/recall).

## Контекст и проблема

Урок 18 построил конвейер «код → прод» с гейтами, но у AI-систем два дополнительных источника изменений, которые не проходят через git push: данные и мир. Модель, не тронутая ни одним коммитом, тихо деградирует — и классический CI/CD этого не увидит, потому что сервис «зелёный». Урок 19 закрывает эту дыру: постоянный мониторинг дрейфа как триггер конвейера, автоматизированное переобучение с автовалидацией и безопасным деплоем, а для RAG-систем — та же логика применительно к векторной базе: свежесть индекса — это «качество модели» RAG, и обновлять его нужно тем же конвейером с smoke-тестами, версионированием и откатом.

## Ключевые тезисы

- **Разделение ролей в стеке — оркестратор ничего не знает про ML, и это правильно:** Airflow управляет порядком/расписанием/retry, MLflow помнит эксперименты и версии, Kubeflow масштабирует на K8s. Попытка одним инструментом закрыть всё — антипаттерн.
- **Автовалидация с двумя гейтами до прода:** сначала абсолютный (метрики в норме? нет → алерт и стоп), затем относительный (лучше текущей prod-версии? нет → отклонить). Новая модель не попадает в прод «потому что новее».
- **Blue-Green vs Canary — выбор по цене ошибки и скорости отката:** Blue-Green — мгновенное переключение и мгновенный откат ценой ×2 сред; Canary — 5→25→100% дольше, но риск на каждом шаге ограничен долей трафика.
- **Data drift ≠ concept drift, и реагируют на них по-разному:** при data drift часто достаточно переобучиться на свежих данных; concept drift может требовать пересмотра фич и постановки задачи — автоматический retrain его не всегда лечит.
- **PSI > 0.2 — практический порог тревоги** (кейс лекции); детекция всегда сравнивает train vs prod распределения, значит нужно *хранить* референсные распределения — ещё один артефакт версионирования.
- **Для RAG «модель» — это индекс:** свежесть векторной базы — такой же объект MLOps, как веса модели: версия снапшота, smoke-test до переключения, rollback при падении hit rate. Прямое расширение «трёхчастного артефакта» урока 18 до четырёх: образ + веса + конфиг + **индекс**.
- **Минимальный MLOps-стек** (итоговый слайд): real-time мониторинг модели, контроль версий модели/данных, настроенные политики обновления версий. Без governance, мониторинга, feature store и CI/CD стек неполный.

## Диаграммы / таблицы

**Пайплайн переобучения (по слайду):**

```
Триггер (расписание | дрейф данных)
  → Загрузка данных (feature store, N дней)
  → Обучение модели (новая версия + MLflow)
  → Автовалидация (accuracy · F1 · AUC) ──не в норме──► Алерт, пайплайн остановлен
  → Сравнение с prod (новая vs текущая) ──хуже──► Уведомление, версия отклонена
  → Деплой (Blue-Green / Canary)
  → В продакшне, мониторинг активен
```

**Инструменты стека (по слайдам):**

| Инструмент | Роль | Минусы |
|---|---|---|
| Airflow | оркестрация: DAG на Python, расписание, retry, UI-мониторинг | не знает про ML-артефакты, требует DevOps-настройки, не для экспериментов |
| MLflow | учёт экспериментов: параметры/метрики/артефакты, Model Registry Staging→Production, lineage | — (без него «никто не знает, какая модель на каких данных обучена») |
| Kubeflow | ML-платформа на K8s: эксперименты, версионирование, GPU/TPU | привязка к K8s, сложная настройка, высокий порог входа |

**Обнаружение дрейфа:**

| Средство | Что делает |
|---|---|
| KS-test, PSI, Chi-square | статистическое сравнение train vs prod распределений |
| Evidently AI | готовые отчёты по дрейфу и деградации, интеграция с Airflow |
| Prometheus + Grafana | real-time: latency, prediction distribution, feature stats; алерты |
| Алертинг + автоответ | почта/PagerDuty + автозапуск retrain-DAG при превышении порога |

**MLOps-пайплайн для RAG (практика):**

| Шаг | Содержание |
|---|---|
| Trigger | новый документ в S3 (S3KeySensor) или cron |
| 1. Load | Airflow DAG запускает загрузчик документов (LangChain DocumentLoader) + change detector (новые/изменённые/удалённые) |
| 2. Process | очистка, chunking 512–1024 токена, metadata tagger (source, date, version), embedding батчами (text-embedding-3-small / all-MiniLM) |
| 3. Upsert | Qdrant / Chroma / FAISS (с поддержкой upsert) |
| 4. Smoke-test | 5–10 тестовых запросов — релевантность до переключения |
| 5. Version | снапшот базы с датой; rollback при падении метрик |
| Мониторинг | retrieval latency (avg, P99), hit rate (similarity > 0.75), user feedback; авто-триггер при hit rate < 0.6 или N+ новых доков; расширенно — Deepeval (precision/recall/F1, contextual precision/recall) |

C4-контейнеры RAG Assistant со слайда «Архитектура»: Frontend (js) + Backend (python) + Vector DB (qdrant/chroma) + Metadata DB (postgres) + Airflow + MLflow + S3 + Embedding-модель + LLM + Мониторинг (Grafana, Prometheus, Langfuse, Evidently).

## Мои выводы

1. **Практика урока — это спецификация нашего ingest-контура.** В финале ([[zubriq-openwebui-deployment]]) обновление базы знаний сейчас событийное/ручное; по лекции его надо оформить как DAG: change detector → chunk+embed → upsert в Qdrant → smoke-test → alias-переключение. Схема пайплайна — готовый кандидат в ДЗ-19 и в ADR финала.
2. **Blue-green для векторной базы дешевле, чем для модели:** две коллекции Qdrant + alias вместо двух сред инференса. Переключение alias после smoke-test даёт мгновенный rollback — беру как целевой паттерн вместо «upsert в живую коллекцию».
3. **Дрейф у нас уже частично мониторится, но не как триггер:** дашборд урока 15 ([[observability-genai]]) видит latency и token-метрики vLLM, но не hit rate и не PSI по запросам. Добавить hit rate (similarity > порога) — самый дешёвый drift-сигнал для RAG; алерт → запуск reindex-DAG замыкает петлю.
4. **Оркестратор нам нужен легче, чем Airflow:** для одного RAG-контура на on-prem паре H100 полноценный Airflow — оверхэд; та же DAG-логика (sensor → 4 шага → smoke) реализуема cron+скриптами или лёгким оркестратором, но интерфейс конвейера (триггеры, версии, rollback) должен быть тем же — это и есть предмет ADR, а не выбор бренда.
5. **RAGAS vs Deepeval:** лектор для расширенного мониторинга называет Deepeval; у нас уже RAGAS в MVP (`/ask` возвращает contexts). Менять фреймворк смысла нет — важно, что contextual precision/recall встают в smoke-гейт пайплайна, а не только в офлайн-оценку.
