# 16. Расчёт ресурсов (Sizing) для приложений и данных

> **Занятие** · 26 июня (пт), 20:00 · 90 мин · преподаватель **Михаил Лебедев**. Блок 4 «Инфраструктура».
>
> **Цели (из ЛК):** прогнозировать требования к вычислительным ресурсам (**CPU, GPU, RAM**) и хранилищам данных; выбирать оптимальные конфигурации инфраструктуры для **минимизации затрат** при соблюдении требований к производительности.
> **Содержание (из ЛК):** методология расчёта ресурсов (CPU, RAM, Disk) для **stateless/stateful**-сервисов и баз данных (**SQL, NoSQL, Vector**) → влияние **RPS**, заданного уровня качества, финансовых ограничений → расчёт **TCO для on-premise** → практика: детальный расчёт ресурсов для всех компонентов учебного проекта (on-premise и облако).
> **Компетенция:** планировать и организовывать надёжную инфраструктуру для AI-систем — производить детальный расчёт ресурсов для компонентов проекта при развертывании on-premise и в облаке.
> **Результаты:** практическое задание (ДЗ-16), конспект лекции, **фрейм «Калькулятор TCO»**.
>
> Связь: открывает инфраструктурную тройку **16 (sizing) → 17 (оптимизация инференса LLM) → 28 (FinOps)**. Для финала ([[final-project-hardware]]) это **обоснование конфигурации 2× H100 NVL 94GB**: sizing vLLM (веса + KV-cache + батчинг под целевой RPS), vector DB для RAG, Postgres/Redis, мониторинг-стек из урока 15 ([[observability-genai]]). TCO on-prem обязателен для юрисдикции РБ (данные не покидают контур, №99-З) — облачная альтернатива считается как baseline для сравнения (у нас есть модуль [[yandex-yc-opentofu]]). Затраты/токены как метрика уже появились в уроке 15 — здесь они становятся деньгами.

## Подготовка / примерка к финалу

- **Эталонный вопрос финала:** почему именно 2× H100 NVL 94GB, а не 4× A100 / облачный API — ответ должен быть числом: веса модели (GB) + KV-cache под N одновременных сессий × context length + headroom, целевой p95 latency и RPS, стоимость за 3 года on-prem vs cloud.
- **Компоненты Суфлёра для расчёта:** vLLM (GPU: VRAM = веса + KV-cache), embeddings-сервис, vector DB (RAM/disk = число чанков × размерность × 4 байта + индекс HNSW), Postgres (Open WebUI, Keycloak), Redis, Prometheus/Grafana/Loki (retention → disk), Pipelines.
- **TCO on-prem:** CAPEX (серверы, GPU, СХД, сеть) амортизация 3–5 лет + OPEX (электричество ~кВт × PUE, охлаждение, ДЦ/стойка, админы, поддержка вендора) vs облако (аренда GPU-инстансов + egress + managed-сервисы).

**Вопросы лектору (заготовка):**
1. KV-cache при батчинге в vLLM: как честно посчитать VRAM под пиковое число одновременных диалогов с контекстом 8–32k, если PagedAttention фрагментирует кэш?
2. Sizing vector DB: считать по сырым векторам или сразу закладывать ×1.5–2 на HNSW-индекс и репликацию? Когда quantization векторов (int8/binary) оправдана?
3. TCO on-prem в РБ: какие статьи OPEX чаще всего забывают (страховка железа, ЗИП, простой при отказе GPU без вендорской замены)?
