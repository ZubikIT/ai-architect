## TL;DR

**Методология sizing.** Отправная точка — тип сервиса: **stateless** (REST API, веб-фронт) не хранит состояние между запросами, легко масштабируется горизонтально, расход CPU/RAM пропорционален **RPS**; **stateful** (Redis, сессии, БД) хранит состояние, требует больше памяти и синхронизации, масштабируется сложнее. **Пять входных параметров расчёта:** RPS, тип нагрузки (чтение/запись/смешанная), среднее время обработки запроса (определяет число потоков/процессов), требования к SLA (uptime, latency, отказоустойчивость → число реплик/бэкапов/HA), финансовые ограничения (бюджет на оборудование, обслуживание, развертывание). Влияние RPS: CPU — больше потоков; RAM — кэши и буферы; Disk — БД и логи, при высоком RPS нужен SSD; сеть — критична при распределённом хранении. Для БД выбор SQL/NoSQL/Vector диктует профиль ресурсов: **SQL** (PostgreSQL) — сложные JOIN, OLTP/OLAP, зависит от объёма/индексации/бэкапов; **NoSQL** (MongoDB, Cassandra) — массовая запись и быстрое чтение, горизонтальное масштабирование (sharding/replication), eventual consistency; **Vector** (Weaviate, Milvus, FAISS) — ANN-поиск, требует **много RAM** (векторы + индекс резидентны), влияние RPS критично.

**TCO (Total Cost of Ownership)** = стоимость оборудования + обслуживание + **энергопотребление** + человеческий ресурс + **стоимость рисков (downtime)** — общие затраты за весь жизненный цикл. Практика на учебном проекте (онлайн-тестирование студентов: React + Flask/Node + PostgreSQL + Redis + Weaviate + ELK; 5000 пользователей, 100 RPS средн., 300 пик): on-premise **980 тыс ₽ разово** vs облако **72 тыс ₽/мес** → простой break-even ≈ 14 месяцев (без учёта OPEX on-prem — электричество, штат, ЗИП; т.е. реальная точка дальше). Вывод лектора: on-prem — если бюджет позволяет и нагрузка стабильна; облако — гибче и выгоднее при росте/неопределённости нагрузки. **Фрейм-калькулятор (xlsx):** тендерная балльная оценка вендоров — «синяя зона» (ТХ + цена: балл цены = MIN(цена)/цена × вес 40, ТХ нормируются на MAX × вес), «серая зона» (бинарные да/нет критерии), санкционный риск; отсекающие критерии → `AND(...)` → «исключено из рассмотрения».

**GenAI-специфика.** VRAM под LLM: **веса = N параметров × M байт** (FP32 → 4 Б, FP16/BF16 → 2 Б, INT8 → 1 Б, INT4 → 0.5 Б) + KV-cache + активации (зависят от batch size и context length, «несколько ГБ»). Примеры: Qwen-7B FP16 ≈ **14 ГБ** только веса; QwQ-32B: FP32 ≈ 138 ГБ, FP16 ≈ **70 ГБ** (64 веса + 5 KV на 1 batch), INT8 ≈ 35 ГБ, INT4 ≈ 18 ГБ. Vector DB на масштабе (SberTech VDB, LAION-400M: 400 млн векторов, dim 512, **FLOAT16 вместо FLOAT32 без значимых потерь**, 5000 ANN RPS): RAM ноды = системная 8.34 + резидентная память данных 39.27 + дисковый кеш 14.54 + IdTracker 12.4 = **54.12 ГБ** — считается по компонентам, а не «векторы × 4 байта». **Фрейм анализа нагрузки:** таблица факт-vs-ожидание (RPS, CPU %, RAM, Disk IOPS, latency, error rate 5xx, SLA, тип сервиса) → выявленные проблемы (CPU 85%, RAM 90% → OOM-kill, IOPS 95%, latency +30%) → рекомендации с приоритетами (горизонтальное масштабирование бэкенда, кэширование Redis, индексы БД, автомасштабирование) → прогноз по месяцам (когда добавлять инстансы).

## Контекст и проблема

Sizing — мост между HLD (уроки 4–5) и деньгами (урок 28 FinOps): архитектор обязан превратить требования (RPS, SLA, бюджет) в конкретные vCPU/RAM/Disk/GPU и обосновать выбор on-prem vs cloud числом, а не вкусом. Ошибка в обе стороны дорогая: недозаклад — деградация SLA и пожарное масштабирование, перезаклад — замороженный CAPEX. Для GenAI добавляется GPU-измерение (VRAM = f(параметры, квантизация, контекст)) и «жадные к RAM» векторные БД.

## Ключевые тезисы

- **Stateless масштабируется горизонтально и считается от RPS; stateful — от объёма состояния** (кэш, сессии, данные) плюс синхронизация. Сначала классифицируй компонент, потом считай.
- **Пять входов расчёта:** RPS, тип нагрузки, среднее время обработки (→ потоки), SLA (→ реплики/HA/бэкапы), бюджет. SLA-требование «99.9%, latency < 200ms» напрямую превращается в количество реплик и HA-конфигурацию.
- **Эталонные конфигурации БД** (ориентиры лектора): SQL 1 ТБ / 1000 RPS / <100 мс / 2 реплики → 3 ноды: 32 vCPU, 128 ГБ RAM, 4 ТБ SSD. NoSQL 5 ТБ / 5000 RPS / eventual → 4 ноды: 32 vCPU, 512 ГБ, 25 ТБ, 10 Гбит/с сеть. Vector 100 млн × dim768 / 1000 ANN RPS → 3 ноды: 32 vCPU, **512 ГБ RAM**, 30 ТБ. Паттерн: у Vector DB узкое место — RAM, у NoSQL — сеть и диск, у SQL — CPU+RAM на JOIN.
- **TCO = оборудование + обслуживание + энергия + люди + риски (downtime).** Пятое слагаемое чаще всего забывают: цена простоя — тоже статья TCO (мост к SLO-математике урока 15: 99.9% = 8.76 ч/год).
- **On-prem vs cloud на учебном проекте:** 980 тыс ₽ CAPEX vs 72 тыс ₽/мес OPEX. Наивный break-even ~14 мес; честный — дальше, если добавить OPEX on-prem, но ближе, если облачная цена растёт с нагрузкой. Решение — не «что дешевле вообще», а «что дешевле на горизонте 3 лет при нашем профиле нагрузки и требованиях к данным».
- **VRAM LLM: параметры × байт/параметр + KV-cache + активации.** Квантизация — главный рычаг sizing: QwQ-32B от 138 ГБ (FP32) до 18 ГБ (INT4). FP16→INT8 обычно почти без потерь качества, INT4 — уже компромисс.
- **Vector DB считается по компонентам памяти** (данные-резидент + дисковый кеш + ID-трекер + системная), FLOAT16 для векторов — халявные −50% RAM.
- **Анализ нагрузки — регулярный фрейм, не разовый:** факт vs ожидание → проблемы → приоритизированные рекомендации → прогноз на 1–3 месяца вперёд. Вход — метрики из observability-контура (урок 15).
- **Выбор вендора железа — взвешенная балльная модель** (xlsx-фрейм): отсекающие критерии (AND), технические характеристики с весами (нормировка на лучшего), цена с максимальным весом (MIN/цена × 40), бинарная «серая зона», санкционный риск отдельной строкой.

## Мои выводы

1. **Главная формула урока для финала:** VRAM = N × M + KV-cache × параллелизм + активации. Наши 2× H100 NVL = 188 ГБ VRAM: 70B-модель в FP16 (~140 ГБ весов) влезает только распределённо на обе карты и почти без KV-запаса; в FP8/INT8 (~70 ГБ) — на одну карту с большим KV-бюджетом под длинные контексты, вторая остаётся под embeddings/reranker/резерв. Это и есть числовое обоснование конфигурации — вписать в ДЗ-16 и финальный ADR.
2. **Vector DB Суфлёра — не про масштаб LAION:** у нас десятки тысяч чанков, не 400 млн; по компонентной модели RAM-нода уложится в единицы ГБ. Значит в sizing финала vector DB — второстепенная строка, а доминанта — GPU и RAM под LLM-стек. Но FLOAT16-векторы берём как дефолт.
3. **TCO-аргумент для РБ:** сравнение «980 тыс vs 72 тыс/мес» из лекции — шаблон, который надо повторить для 2× H100 против аренды GPU в облаке; при этом у нас есть неценовой отсекающий критерий (данные в контуре, №99-З), поэтому облако в ДЗ считаем как baseline для демонстрации методики, а не как реальную альтернативу. Санкционный риск из xlsx-фрейма — легитимная строка оценки вендора в нашей юрисдикции.
4. **Фрейм анализа нагрузки замыкается на урок 15:** колонки таблицы «факт vs ожидание» — это ровно метрики нашего дашборда (sufler_*, vllm:*_tokens_total, nvidia_smi_*). Прогноз «когда добавлять инстансы» для GPU-инференса — мост к уроку 17 (батчинг/квантизация вместо покупки третьей карты).
