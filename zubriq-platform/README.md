# ZubrIQ — архитектура как она есть

Описание **реально работающей** платформы `zubriq.by`: что из чего состоит, где физически живёт, как связано, какие решения приняты и чем за них платят. Не проект и не план — снимок состояния.

Источник фактов — конфигурация репозиториев `zubriq/*`, `ai/*`, `devops/*` и живые ответы сервисов. Где факт не проверен, это сказано прямо.

> ## ⚠️ Репозиторий больше не публикуется наружу
>
> Здесь есть внутренняя адресация, пути Vault, инвентарь узлов и имя банковского клиента. Поэтому публичные зеркала **удалены из репозитория** — сначала был заблокирован push-URL, затем ремоуты убраны совсем:
>
> ```
> origin	git@git.artcloud.by:ai/architect.git   ← единственный remote
> ```
>
> Восстанавливать `github` и `gitlab-com` нельзя, пока эта папка в истории `main`: детали уже в коммитах, и один push опубликует их целиком. Нужна публичная копия курса — только отдельный репозиторий с чистой историей.
>
> **Остаётся один канал, который отсюда не контролируется:** `gitlab.mtbank.by/course/architect` — pull-зеркало, оно подтягивает `main` само по расписанию. То есть внутренняя топология АртКлауда уедет в GitLab клиента. Если это нежелательно — зеркало отключается на стороне банка, локальными средствами это не решается.

## Как это соотносится с курсовым проектом

[`../final-project/`](../final-project/) — архитектурный слой **над** этой платформой: проект закрытого air-gapped контура для ЗАО МТБанк (GraphRAG, мультиагентный слой, ACL на узлах графа). `zubriq.by` — публичная копия того же решения, работающая как коммерческий продукт.

| | ZubrIQ (эта папка) | Финальный проект |
|---|---|---|
| Что это | работающая платформа, публичный доступ, биллинг в BYN | проект закрытого контура для МТБанка |
| Модели | свои self-hosted **и** коммерческие через OpenRouter/Mistral | **только** self-hosted, облачные API запрещены критерием приёмки |
| Контур | гибридный: часть запросов уходит вендору | air-gapped |
| Состояние | в проде, мигрирует с ВМ в кластер Talos | MVP + пакет документации |

Граница между ними проходит ровно по **LiteLLM**: в ZubrIQ он маршрутизирует и в закрытый контур, и наружу, а разрешение выдаётся ключу; в проектируемом контуре внешнего плеча нет вовсе.

Суфлёр из курсового проекта существует и в этой инфраструктуре: ВМ 237, векторная база — Qdrant на `10.100.1.46:6333`, коллекция `lpa`.

## Кратко, одним экраном

**ZubrIQ** (ООО «АртКлауд») — платформа доступа к языковым моделям в юрисдикции РБ, с оплатой в BYN и счетами юрлицам. Ядро — **LiteLLM**: выпускает virtual keys, ведёт бюджеты, пишет потребление в Postgres, откуда консоль считает счёт, и решает, какие модели ключу видны.

Два плеча под шлюзом:

- **своё железо** — LXC 100 «llama» на pve4, 4× Tesla V100 SXM2 16 ГБ, vLLM нативно, `Qwen3.8-27B-AWQ-INT4` (плотная мультимодальная 27B, с 18.09.2026 вместо MoE `Qwen3.6-35B-A3B-AWQ`), tensor-parallel по 4 картам, окно 262 144, эндпоинт `10.100.1.200:80`; она же отдаёт и зрение — отдельная 4B погашена;
- **внешнее** — сотни проприетарных моделей через один upstream-аккаунт OpenRouter плюс прямые маршруты Mistral и Alibaba.

Права на второе плечо выдаются **на уровне ключа** (поле `models` при выпуске) — это единственное место, где проходит граница «контур / не контур».

Поверх — продукты: чат, консоль (`console.zubriq.by`), документация, Drive, Академия, `zq`, MCP-шлюз. Инфраструктура — Proxmox (pve1–pve4) плюс кластер Talos (`10.100.1.80–.90`, LB `10.100.1.91–.99`); платформа **в середине переезда**, и пути отката намеренно живы.
