# Платформенный слой

Всё, что не является продуктом, но без чего не работает ни один продукт. Адреса и пути — в [инвентаре](inventory.md).

## LiteLLM — центр платформы

Единая точка входа ко всем моделям, OpenAI-совместимый API. Публичные имена — `api.zubriq.by` (клиентам) и `llm.acl.by` (внутренним потребителям), обе указывают в ingress кластера `10.100.1.91`.

Совмещает четыре роли, и именно совмещение делает его центром:

| Роль | Что конкретно |
|---|---|
| **Ключи** | virtual keys на пользователя и организацию; выпуск — из консоли (`app/Services/LiteLlm.php`) |
| **Бюджеты** | лимит на ключ, отказ на входе до обращения к модели |
| **Каталог** | модели и цены; клиент зовёт по имени, не зная, где модель физически |
| **Учёт** | потребление в токенах и деньгах → таблица `LiteLLM_SpendLogs` → счёт |

Консоль ходит в шлюз по **внутреннему** адресу `http://10.100.1.201:4000`: hairpin через `api.zubriq.by` из контура не работает — сертификат self-signed.

### Каталог моделей

**Своё плечо.** Алиас `zubr` → `openai/qwen3.6-35b` на `http://10.100.1.200:80/v1`; отдельно `qwen3.6-35b` тем же маршрутом. VL — `zubr-vision` и `qwen3-vl-4b` на `http://10.100.1.200:8001/v1`. Запрос не покидает контур.

**Внешнее плечо.** Wildcard-маршрут `openrouter/*` — сотни проприетарных моделей через **один upstream-аккаунт**: клиент зовёт `openrouter/<vendor>/<model>`, поштучно модели не перечисляются, новинки вендоров появляются без правки конфига. Спенд считает встроенная cost-map LiteLLM, консоль начисляет BYN-маржу сверху. Плюс прямые маршруты: `mistral-medium-2505`, `codestral`, `qwen-coder-plus` (Alibaba DashScope).

**`zubr-coder`** указывает на пилот llama.cpp на том же GPU-боксе либо на внешний фолбэк — переключение маршрута делает CI по тегу.

> Для [курсового проекта](../../final-project/) пригодно **только своё плечо**: критерий приёмки прямо запрещает облачные API. Это не дефект платформы — это разные задачи.

## Собственный инференс

**Железо:** LXC 100 «llama» на `pve4`, 4× NVIDIA Tesla V100 SXM2 по 16 ГБ.

**Движок:** vLLM **нативно через systemd, без docker** — ради прямого контроля над VRAM и порядком запуска.

**Модель:** `Qwen3.6-35B-A3B-AWQ` (~19 ГБ, сборка QuantTrio, архитектура `qwen3_5_moe`) — MoE: 35 млрд параметров всего, около 3 млрд активных на токен. Tensor-parallel по четырём картам, `--max-model-len 65536`, served name `qwen3.6-35b`, лежит в `/opt/models/` на диске LXC.

**Веса** — в MinIO (бакет `models`), синхронизация на бокс через `mc` в `ExecStartPre` юнита (`scripts/model-sync.sh`). Бокс восстановим без ручного копирования моделей.

**Откат:** предыдущая `Qwen3.5-27B-AWQ` оставлена и на диске, и в MinIO — возврат = revert `vllm.service`.

**Ограничение, определяющее дизайн:** VRAM эксклюзивна. 64 ГБ суммарно не хватает на основную модель и пилотный `Qwen3-Coder-Next-80B-A3B` одновременно, поэтому юнит llama.cpp объявляет `Conflicts=vllm.service`. Отсюда правило: **не гонять деплой `ai/vllm`, пока пилот не закрыт** — `restart vllm` убьёт llama.cpp.

Выбор MoE с малой активной частью — прямое следствие того же ограничения: на V100 плотная модель сопоставимого качества не даёт приемлемой скорости.

## Идентификация

Keycloak на ВМ 219 (`10.100.1.19`), публичное имя `id.zubriq.by`, realm `zubriq` («ZubrIQ»). Клиенты: `console`, `chat`, `drive`. Группы кладутся в токен отдельным scope `groups` и generic protocol mapper; продукты решают по группам, а не по внутренним спискам. Сервис-аккаунт клиента `console` имеет роли `view-users`/`manage-users` в `realm-management`.

Учётные записи приходят федерацией из FreeIPA (`10.100.1.15`). Конфигурация — `devops/opentofu/modules/keycloak/zubriq.tf`.

**Известное свойство федерации:** `cache.policy=DEFAULT` держит старые группы. После правки членства в IPA требуется `POST /admin/realms/<realm>/clear-user-cache` плюс federation sync (`user-storage/{cid}/sync?action=triggerChangedUsersSync`). Проверить claim без логина пользователя: `clients/{uuid}/evaluate-scopes/generate-example-id-token?userId=...`. То есть **отзыв прав не мгновенен** и требует процедуры, а не только правки группы.

### Retrieval базы знаний — в Postgres, а не в векторной БД

Поиск чата живёт в `console/app/Chat/PgVectorRetriever.php`: таблица `kb_chunks` в той же Pigsty, конвейер **вопрос → bge-m3 → кандидаты → bge-reranker-v2-m3 → top-K**. Режим `hybrid` добавляет полнотекстовую ветку (`kb_chunks.fts`, русский словарь) — точные номера статей вектор размывает, полнотекст ловит дословно; слияние RRF, финальный порядок всё равно за реранкером.

**Qdrant заменён по итогам пилота 01.08.2026** (`dify/kb/codes/pilot_vectors`). Вывод пилота стоит процитировать, потому что он контринтуитивен: **качество то же — «решает реранкер, а не хранилище»**. Qdrant, pgvector и pgvector+FTS дали hit@1 89 % и один и тот же промах, то есть выбор хранилища на качество не влияет вовсе.

Второе утверждение того же пилота — что выигрыш 67 % → 89 % против прод-Dify дала **нарезка с заголовком «Кодекс — Статья N»** — при проверке (12.09.2026) оказалось **интерпретацией, а не замером**. Между двумя системами различались одновременно размер куска (~1500 символов против child-кусков Dify), нарезчик и реализация hybrid+rerank; изолированного A/B по заголовку нет, а в golden адресуют статью 2 вопроса из 61. Чем именно объясняются 22 п.п., не установлено. Отдельный замер заголовка — в [курсовом проекте](../../final-project/docs/eval-report.md#где-адрес-действительно-работает): он помогает вопросам, которые адресуют документ, и не меняет ничего на семантических.

Следствие для архитектуры: векторное хранилище здесь — не то место, где создаётся качество. Поэтому второе stateful-хранилище ради него заводить незачем, и по той же причине скоры в панели «Источники» показываются реранкерские (0..1), а не косинусные — они честнее.

Langfuse развёрнут в OSS-редакции: **admin-API доступен только в Enterprise**, поэтому провайдер OpenTofu для него не используется и project-ключи выпускаются руками. Это зафиксированное нарушение принципа «всё в IaC».

Чего нет: **сквозного трейсинга через продукты**. Путь запроса виден по частям — логи продукта, логи шлюза, трассировка Langfuse, — но единого идентификатора, связывающего действие пользователя в чате с вызовом модели, нет. Разбор инцидента идёт сопоставлением по времени.

## Периметр

Nginx Proxy Manager на `10.100.1.12`: TLS, маршрутизация по именам, статика вроде Digital Asset Links для TWA-приложения чата.

Сертификаты Let's Encrypt. Для поддоменов — **wildcard `*.zubriq.by` через DNS-01 Cloudflare**: выпуск по каждому имени упёрся в лимит «5 сертификатов на идентификатор в неделю» (поймали на `langfuse.zubriq.by`); wildcard — отдельный идентификатор, выдаётся сразу и покрывает будущие поддомены. Токен CF account-wide, лежит в Vault.

Конфигурация — `devops/opentofu/modules/npm/proxy_host_zubriq.tf`; NPM остаётся перед кластером и после переезда: он же и есть механизм переезда — цель имени меняется в одном месте.

Два нетривиальных места в конфиге периметра:

1. **`X-Forwarded-Port: 443` проставляется вручную.** После cutover цепочка стала NPM(443) → ingress(80) → под; ingress ставит `X-Forwarded-Port: 80`, Laravel строит из него адрес редиректа и выдавал `https://console.zubriq.by:80/admin`. Чинить на ingress нельзя — сниппеты запрещены (`allow-snippet-annotations=false`), но он доверяет входящим заголовкам (`use-forwarded-headers=true`).
2. **Легаси-пути OWUI на апексе** (`/auth`, `/c/`, `/oauth/`, `/workspace`, `/admin`, `/channels/`, `/playground`) отдают 301 на `owui.acl.by`. Хоп через публичный апекс убирать нельзя: туда возвращается Google OAuth (`GOOGLE_REDIRECT_URI = https://zubriq.by/oauth/google/callback` — внутреннее имя в консоли Google не зарегистрируешь). `/api/` из списка исключён — в Phase 2 он проксируется на консоль, иначе 301 сломал бы POST Google One Tap.
