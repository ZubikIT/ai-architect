# Безопасность: где проходит граница контура

Платформа продаёт юрисдикцию — «данные остаются в контуре РБ». При этом часть трафика по замыслу уходит вендору через OpenRouter. Оба утверждения верны одновременно, и весь вопрос в том, **чем именно разделены эти два режима**.

## Два режима доступа

| | Закрытый режим | Внешний режим |
|---|---|---|
| Куда идёт запрос | `10.100.1.200:80` — свой GPU-бокс | OpenRouter / Mistral / DashScope |
| Что покидает контур | ничего | **промпт целиком, вместе с вложенным контекстом** |
| Модели | `zubr`, `qwen3.6-35b`, `zubr-vision`, `qwen3-vl-4b` | `openrouter/*`, `mistral-medium-2505`, `codestral`, `qwen-coder-plus` |
| Кому нужен | контурные сценарии, работа с чувствительными данными | доступ к сильным проприетарным моделям |

Внешний режим — не компромисс, а продукт: «второй режим доступа» с zubriq.by. Ошибкой была бы не его продажа, а выдача его тем ключам, которым он не положен.

## Единственный барьер — поле `models` у ключа

Разрешение действует **на уровне virtual key**, а не пользователя, интерфейса или сети. При выпуске ключа поле `models` ограничивает список разрешённых; если оно задано, внешние маршруты в него не входят и запрос отклоняется **до** обращения к вендору.

Правило, зафиксированное в конфигурации: контурным и секьюрным ключам (Shield, инфра, s3-docs, call-analytics) внешние модели **не выдаются** — их список ограничен своими (`zubr`/`qwen3.6-35b`).

Что здесь хорошо:

- **Барьер один и проверяем.** Чтобы ответить «может ли этот клиент утечь наружу», достаточно посмотреть одно поле у его ключей.
- **Проверка до вызова.** При проверке «после» данные уже ушли бы.
- **Приложение не может себя расширить.** Ни чат, ни консоль, ни `zq`, ни код клиента не влияют на список — он живёт при ключе.

Что плохо, и это надо называть прямо:

- **`models` пустой = видно всё, включая `openrouter/*`.** Умолчание работает в сторону разрешения. Забыли ограничить при выпуске — получили внешний доступ по умолчанию.
- **Граница логическая, не сетевая.** Сетевого запрета исходящего трафика для контурного профиля нет; ошибка в конфигурации ключа ничем на уровне сети не компенсируется. Защита в глубину однослойная.
- **Режим не показан пользователю.** В чате не видно, покинул ли вопрос контур; различие читается только по имени модели.

## Грабли доступа Open WebUI (разобраны, закреплены в коде)

Старый чат заморожен, но правила остаются актуальными для понимания модели доступа продукта:

- **Admin-роль.** OWUI читает админ-роль из claim `OAUTH_ROLES_CLAIM` (дефолт `roles`), а Keycloak кладёт IPA-группы в claim **`groups`** — `roles` пуст. В compose нужны `OAUTH_ROLES_CLAIM=groups` и `OAUTH_ADMIN_ROLES=admins`. Роль пересчитывается **только на новом OIDC-логине** (logout → login, не refresh).
- **Видимость кастомной модели для не-админов гейтит `access_grants`** — новая модель доступа OWUI, а НЕ `access_control` и не `model_order_list`. Провайдер `ncecere/openwebui` пишет только legacy `access_control` и грант не создаёт, поэтому `openwebui_model.*` виден только владельцу. Обход закодирован: `null_resource.public_model_grants` в `modules/openwebui/model_access.tf` шлёт `POST /api/v1/models/model/access/update` с публичным грантом `{principal_type:"user", principal_id:"*", permission:"read"}`. Чтобы открыть новую модель — добавить её id в `for_each`.
- **`read_groups`/`write_groups`** тоже идут через access_grants; **у Google-юзеров нет групп Keycloak**, поэтому групповое ограничение их отрезает. Для air-gapped прода МТБанка Google-провайдер убирается.

Диагностика логики видимости — `utils/models.py::get_filtered_models`: модель без гранта и без записи в БД видит только админ.

## Секреты

Всё в Vault (кластер `10.100.1.52–.54`, raft HA, auto-unseal через transit): ключи провайдеров, пароли БД, токены API. В репозиториях их нет, в образы не запекаются. Полный перечень путей — в [инвентаре](inventory.md).

Исключение, зафиксированное осознанно: **админ-токен OWUI создаётся руками** в интерфейсе и кладётся в `secret/openwebui` — провайдер не умеет его выпускать. То же с project-ключами Langfuse (admin-API Enterprise-only).

## Общий ключ Qdrant — известная дыра изоляции

Ключ API Qdrant **один на инстанс** `10.100.1.46:6333`. (Продуктовый retrieval чата идёт не через него, а через `kb_chunks` в Pigsty — но инстанс живой и данные в нём есть.) Он даёт доступ и к коллекции `lpa` Суфлёра, и к коллекциям `shield_*` сканера. В Vault пути разные (`secret/qdrant/api` и `secret/shield/qdrant`), но ключ за ними тот же.

Разделение сегодня — **только по соглашению об именах коллекций**. Изоляция потребует включить JWT RBAC в Qdrant и выдавать scope-токены. Записано в коде инфраструктуры как явное предупреждение, а не обнаружено при аудите.

## Данные, чувствительные не там, где ожидают

1. **Диалоги** — БД чата (кластер) и БД OWUI (legacy).
2. **Файлы клиентов** — Drive (ВМ 261) и MinIO.
3. **Потребление** — `LiteLLM_SpendLogs` в Pigsty: кто, какой моделью и сколько пользовался. Коммерческая тайна клиента даже без содержимого.
4. **Langfuse** — **содержит промпты и ответы**. Живёт на ВМ 205, доступ у инженеров платформы. По чувствительности равен пункту 1, по вниманию при настройке доступа — обычно нет.
5. **Логи периметра** — NPM: адреса, имена, метаданные обращений.

Четвёртый пункт — самый недооценённый: наблюдаемость почти всегда имеет более широкий круг доступа, чем продуктовая БД, и хранит то же содержимое.

## Чего нет и что не проверено

- **Ретеншн.** Сколько живут диалоги, трассировки Langfuse и логи NPM — не установлено. Для платформы, продающей юрисдикцию, срок хранения — часть предложения.
- **Удаление по требованию** из всех пяти мест списка выше — сквозной процедуры не видел.
- **Шифрование бэкапов** — не проверял.
- **Межарендное разделение** в БД консоли — разделение по организации есть, проверок на уровне запросов не смотрел.
- **Red teaming моделей** — методика [описана в курсовом проекте](../../final-project/docs/adr/0018-security-testing.md), к платформе не применялась.

## Что стоило бы изменить

По убыванию отношения эффекта к затратам:

1. **Перевернуть умолчание `models`**: пустой список должен означать «только свои модели». Изменение маленькое, закрывает целый класс ошибок выпуска.
2. **Сетевой запрет исходящего трафика** для узлов, обслуживающих контурные ключи, — второй слой под логическим барьером.
3. **JWT RBAC в Qdrant** — убрать общий ключ на два независимых потребителя.
4. **Показывать режим в интерфейсе** — пользователь должен видеть, что вопрос уходит вендору, до отправки.
5. **Определить ретеншн** и привести Langfuse к тому же режиму доступа, что и продуктовые данные.
