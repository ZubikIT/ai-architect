# Обзор: что такое ZubrIQ

## Продукт

**ZubrIQ** — платформа доступа к языковым моделям, работающая в юрисдикции Республики Беларусь. Владелец — ООО «АртКлауд». Продаётся организациям и частным пользователям: оплата в BYN, счета юридическим лицам, учёт потребления по токенам.

Ценность, ради которой платформа существует, — не сам чат и не сама модель. Чат можно взять открытый, модель — арендовать. Платформа продаёт то, чего в открытых компонентах нет:

1. **Юрисдикция.** Данные и расчёты остаются в контуре РБ; для части клиентов это условие, при котором разговор вообще начинается.
2. **Расчёты в BYN** со счетами и закрывающими документами. Зарубежная подписка в валюте для белорусского юрлица — отдельная задача, и платформа снимает её целиком.
3. **Единая точка доступа** к своим и чужим моделям с общим учётом, бюджетами и ключами — вместо зоопарка аккаунтов у разных вендоров.

Первые два пункта — это и есть причина, по которой платформа не сводится к «поставили Open WebUI».

## Из чего состоит

Продукты платформы, все под доменом `zubriq.by`:

| Продукт | Домен | Что это |
|---|---|---|
| **Чат** | `zubriq.by/chat` | собственный брендовый AI-чат: React + Vercel AI SDK, стриминг ответов; есть приложение в Google Play (TWA-обёртка) |
| **Консоль клиента** | `console.zubriq.by` | Laravel + Filament: организации, API-ключи, потребление, кошелёк, счета |
| **Документация** | `docs.zubriq.by` | документация платформы |
| **Хранилище** | `drive.zubriq.by` | документы клиентов в контуре РБ |
| **Академия** | `academy.zubriq.by` | обучение: курс → практика в Jupyter → лаборатория сценариев → пилот |
| **Консольный инструмент** | `code.zubriq.by`, `get.zubriq.by` | `zq` — форк Qwen Code под платформу; установка через `get`, есть tap для Homebrew |
| **MCP-шлюз** | `mcp.zubriq.by`, `inspector.zubriq.by` | доступ агентов к инструментам по Model Context Protocol |
| **Идентификация** | `id.zubriq.by` | единый вход для всех продуктов |
| **API** | `api.zubriq.by` | OpenAI-совместимый эндпоинт шлюза моделей — то, что покупает клиент |

Плюс сервисы, которые клиент не видит, но без которых платформа не работает: аналитика посещаемости (`stats`), статус-страница (`status`), наблюдаемость LLM-трафика (`langfuse`), эмбеддинги (`embeddings`).

## Кто пользователи

- **Клиент-организация** — покупает доступ по API либо рабочие места в чате; платит в BYN, получает счета. Внутри организации — сотрудники с ключами и бюджетами.
- **Частный пользователь** — чат с оплатой с кошелька.
- **Разработчик** — берёт OpenAI-совместимый ключ и подключает платформу как провайдера в своём коде или в `zq`.
- **Персонал платформы** — админ-панель консоли, доступна только сотрудникам по домену почты.

## Ключевое архитектурное свойство

**Шлюз моделей — не деталь реализации, а центр платформы.** Через него проходит каждый запрос к любой модели, и он одновременно:

- выпускает и проверяет ключи (virtual keys);
- ведёт бюджеты и лимиты;
- пишет фактическое потребление в базу, из которой считается счёт;
- решает, какие модели ключу видны, — то есть проводит границу между закрытым контуром и внешним миром.

Из этого следует и главное ограничение: **шлюз — единая точка отказа для всей платформы**. Ни один продукт не работает, когда он недоступен. Это уже проявилось на практике и стало причиной переезда в кластер — разобрано в [решениях](decisions.md) и [эксплуатации](operations.md).

## Состояние: платформа в середине переезда

Историческая топология — виртуальные машины и контейнеры на Proxmox, деплой по SSH из CI. Целевая — кластер Talos Linux с GitOps через ArgoCD.

Переехали: шлюз моделей, консоль. Осталось на ВМ: часть продуктовых сервисов и всё, что связано с GPU (инференс на кластер не переносится — карты физически в боксе).

Это описание фиксирует **промежуточное** состояние. Оно не «беспорядок, который надо скрыть»: пути отката осознанно оставлены живыми, и в документе они названы. Смешанная топология — цена управляемого переезда, и она временная по замыслу, а не по обещанию.
