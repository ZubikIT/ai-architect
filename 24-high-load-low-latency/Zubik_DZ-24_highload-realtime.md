# ДЗ-24 · Архитектура для высоких нагрузок и Real-time обработки

**Студент:** Александр Зубик · **Курс:** AI Architect (OTUS) · **Дедлайн:** 20.08.2026 · **Статус:** не сдано

## Задание

**Цель:** спроектировать высоконагруженную архитектуру real-time AI-сервиса с кэшированием, горизонтальным масштабированием и асинхронной обработкой.

**Задача:** сервис вырос — нагрузка **10 000 RPS**, требование **Latency < 200 мс**.

**Шаги выполнения:**

1. **Caching Strategy** — внедрить кэширование. Где? (CDN, API Gateway, Redis для эмбеддингов — Semantic Cache). Описать алгоритм Semantic Cache.
2. **Scaling** — схема горизонтального масштабирования Inference-подов (KEDA autoscaling по метрике очереди запросов).
3. **Async Processing** — для тяжёлых запросов переход на асинхронную модель (queue-based).
4. **Global Distribution** *(опционально)* — если пользователи по всему миру: Geo-DNS и Edge computing.

**Формат сдачи:** схема High-Load архитектуры с пояснительной запиской по выбранным паттернам оптимизации.

**Вспомогательные материалы:** [Semantic Cache · Azure Cosmos DB (Microsoft Learn)](https://learn.microsoft.com/ru-ru/azure/cosmos-db/gen-ai/semantic-cache); [KEDA](https://keda.sh/).

## Критерии оценки

Статус «Принято», если:

- [ ] **Адекватность мер:** Semantic Cache реально снижает нагрузку на LLM
- [ ] **Масштабируемость:** решение выдержит рост нагрузки
- [ ] **Latency:** предложенные меры (кэш, edge) направлены на снижение задержек

### План

Объект проектирования — тот же сквозной RAG-ассистент, что в ДЗ-20 и финальном проекте, но в сценарии «сервис вырос до 10 000 RPS».

1. **Бюджет латентности.** Разложить 200 мс по участкам (edge/gateway → кэш-лукап → ретрив → инференс → сеть) и показать, что без кэша бюджет не сходится: prefill+decode LLM сам по себе больше 200 мс. Отсюда вывод — 200 мс достижимы только при высокой доле ответов, не доходящих до генерации.
2. **Многоуровневый кэш.** CDN/edge для статики и повторяющихся публичных ответов → кэш на API Gateway (полное совпадение, ключ = хэш нормализованного запроса + версия промпта + версия индекса) → **semantic cache** в Redis (эмбеддинг запроса → ANN-поиск → порог косинусной близости → выдача) → **prefix/KV cache** в vLLM для системного промпта и общего контекста. Алгоритм semantic cache расписать по шагам с порогами, TTL, инвалидацией по версии индекса/промпта и разделением по арендатору (риск ПДн и нерелевантных ответов — урок 24, слайд 15).
3. **Масштабирование.** KEDA `ScaledObject` по глубине очереди (Kafka/Redis Streams) и по времени ожидания, а не по CPU; отдельно — почему HPA по CPU для GPU-подов не работает; учёт долгого старта и прогрева (`initialDelay`, warm pool, minReplicaCount > 0); разведение prefill/decode при необходимости.
4. **Асинхронная обработка.** Классификация запросов на быстрые (синхронный путь) и тяжёлые (queue-based): `202 Accepted` + callback/polling, результат в S3/БД — тот же контракт, что [[async-callback-200ok-pattern]] и урок 23; DLQ и идемпотентность обязательны.
5. **Global distribution.** Geo-DNS → региональные точки присутствия, edge для препроцессинга и лёгких моделей; отдельно — ограничение №99-З для нашего реального кейса (ПДн не покидают РБ), то есть глобальная схема даётся как общий паттерн с оговоркой применимости.
6. **Схема** — C4-подобная диаграмма в Mermaid + таблица «решение → какой НФТ закрывает → чем платим».
