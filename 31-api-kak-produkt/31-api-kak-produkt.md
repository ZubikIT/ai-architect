## TL;DR

**API как продукт — это подход, при котором программный интерфейс рассматривается не как технический инструмент, а как самостоятельный коммерческий продукт** со своими пользователями, ценностью и метриками. Пять принципов дизайна: **Consumer-First** (начинать с вопроса «кто и как будет вызывать метод», а не «какие данные лежат в базе»), **Design-First** (сначала контракт OpenAPI, потом код — правка на этапе спецификации стоит 5 минут, на этапе готового кода — дни), **Consistency**, **Evolvability** и **Discoverability**. Жизненный цикл держится на трёх опорах: **версионирование** (URI-схема `/v1/` для публичных API как проверенный дефолт + явная deprecation policy с Sunset-заголовком), **документация как часть продукта** (OpenAPI/Swagger, Postman, Developer Portal) и **API Gateway** (аутентификация, rate limiting, мониторинг, роутинг версий). У AI API поверх этого четыре собственные особенности: **недетерминированность** (нужны `temperature`/`seed` и их объяснение в документации), **высокая latency** (streaming через SSE и timeout-политика), **дорогой инференс** (rate limiting и кэш критичны) и **версионирование моделей** — обновление модели меняет поведение, поэтому нужна политика стабильности. Путь наружу — четыре стадии: **Internal → Dev Preview → Paid Beta → Public API**. Главный вывод разбора кейсов: **потребитель определяет всё** — протокол, документацию, монетизацию, глубину изоляции; Enterprise и SMB — принципиально разные продукты, и один API, сделанный для обоих, будет неудобен обоим.

## Контекст и проблема

Вопрос, с которого начинается лекция: почему на API надо смотреть как на продукт, а не как на техническое решение. Ответ — в том, что у API есть потребители, и они разные:

| Потребитель | Что это | Что для него главное |
|---|---|---|
| **Внутренние команды** | микросервисы, фронтенд, мобильное приложение | скорость и стабильность |
| **Партнёры** | B2B-интеграции | контракты, SLA, версионирование, поддержка |
| **Внешние разработчики** | third-party, marketplace | **онбординг и документация** |
| **Конечные пользователи** | через SDK и виджеты | простота, минимальный time-to-value |

**Один API может обслуживать несколько типов потребителей одновременно** — и именно отсюда растут все конфликты требований.

## Ключевые тезисы

### Пять принципов хорошего API-дизайна

1. **Consumer-First** — начинайте с вопроса «кто и как будет вызывать этот метод», а не «какие данные у меня есть в базе».
2. **Design-First** — сначала контракт в OpenAPI, потом реализация. Экономика простая: неудобство, найденное на этапе спецификации, правится за 5 минут; на этапе готового кода — за дни.
3. **Consistency** — единые соглашения по именованию, структуре ошибок, форматам дат во всех эндпоинтах: потребитель не должен каждый раз «учить» новый стиль.
4. **Evolvability** — API будет меняться, думайте об этом с первого дня: как вносить изменения, не ломая существующих потребителей.
5. **Discoverability** — потребитель должен понимать возможности API без звонка в поддержку: понятные названия методов, примеры, описания ошибок — часть продукта.

### Типы API и когда что выбирать

| Тип | Суть | Когда |
|---|---|---|
| **REST** | HTTP-методы над ресурсами, обычно JSON; просто и гибко, но при больших объёмах требует нескольких запросов | **публичный API для внешних разработчиков**; при стриминге ответов LLM добавляем **SSE** |
| **gRPC** | HTTP/2 + Protocol Buffers, 4 типа взаимодействия (унарный, серверный/клиентский стрим, двунаправленный) | **микросервисы, где важна скорость** — в основном внутренние |
| **GraphQL** | клиент сам определяет форму и размер ответа, один запрос вместо нескольких | сложный UI-клиент с вложенными запросами; хорошо ложится на паттерн **BFF** |
| **WebSocket** | постоянный открытый канал, данные в реальном времени; дороже по ресурсам | real-time двусторонняя связь: чаты, игры, оповещения |
| **SOAP** | XML, встроенная обработка ошибок, разные транспорты; объёмные сообщения | legacy / enterprise-интеграции |

### Жизненный цикл: версионирование

| Стратегия | Как | Оценка |
|---|---|---|
| **URI versioning** | `/api/v1/predict`, `/api/v2/predict` | самый популярный для публичных API: просто, понятно, легко кэшировать — **рекомендовано для внешних** |
| **Header versioning** | `Accept: application/vnd.api+json;version=2` | чистые URL, но сложнее тестировать и документировать; так сделан GitHub API |
| **Deprecation policy** | поддержка старой версии N месяцев после выхода новой | предупреждать через **Sunset-заголовок**, changelog, email; минимум несколько месяцев до отключения |

### Документация как часть продукта

- **OpenAPI / Swagger** — стандарт описания REST API, автогенерация документации и SDK, Swagger UI как интерактивная документация;
- **Postman / Insomnia** — среда тестирования и коллекции запросов, публикация документации, mock-серверы;
- **Developer Portal** — центральный хаб: API reference, guides, changelog, примеры кода, комьюнити (образцы — Stripe Docs).

### API Gateway: четыре функции

| Функция | Содержание |
|---|---|
| 🔐 **Аутентификация и авторизация** | API-ключи, OAuth 2.0, JWT; разграничение доступа по тарифам |
| ⏱ **Rate limiting** | защита от перегрузки; квоты «запросов в минуту / в месяц» по тарифному плану |
| 📊 **Мониторинг и логирование** | latency, error rate, usage — **основа для аналитики и биллинга** |
| 🔀 **Версионирование и роутинг** | одновременная поддержка v1/v2, плавный переход без downtime |

### Монетизация

**Freemium** (бесплатный тариф с ограничениями, платные снимают лимиты) · **Pay-per-use** (оплата за фактическое потребление: запросы, токены, гигабайты; у клиента нет фиксированных затрат) · **Subscription tiers** (фиксированная плата за уровень доступа Starter / Pro / Enterprise — предсказуемая выручка).

### Чем AI API отличается от обычного

**AI API = обычный API + специфика ML: недетерминированность, высокая стоимость, версии моделей.**

| Особенность | Следствие для дизайна |
|---|---|
| **Недетерминированность** — одинаковый запрос даёт разный ответ | параметры `temperature`, `seed` **и их объяснение в документации** |
| **Высокая latency** — инференс медленнее обычного API | streaming (SSE/WebSocket) и явная timeout-политика ради UX |
| **Дорогой инференс** — стоимость зависит от модели и объёма токенов | rate limiting и кэширование критичны |
| **Версионирование моделей** — обновление модели меняет поведение | **политика стабильности**: клиент должен знать, когда под ним меняется модель |

Последний пункт — самый недооценённый: в обычном API breaking change виден в контракте, а в AI API поведение может измениться при неизменной спецификации.

### Мультитенантность в AI API

1. **Изоляция данных по тенанту** — каждый клиент видит только свою историю запросов, файн-тюнинги и настройки; реализация: `tenant_id` в JWT или API-ключе + row-level security в БД.
2. **Rate limiting на уровне тенанта** — квоты по тарифу (Starter 100 req/min, Pro 1000 req/min), причём **отдельный лимит на параллельные запросы** — особенно для LLM-инференса.
3. **Изоляция вычислительных ресурсов** — Enterprise часто требует dedicated inference (выделенный GPU/нода); shared дешевле, но порождает «шумных соседей». Решение — приоритетные очереди + burst limits.

Это ровно урок 26, но развёрнутый наружу: там изоляция была требованием безопасности, здесь она становится **предметом тарифа**.

### Монетизация AI API

| Модель | Механика |
|---|---|
| **Оплата за токены** | input и output считаются отдельно, **output дороже input в 3–5 раз**; важно показывать расход в реальном времени и давать возможность оценить стоимость **до** отправки запроса |
| **Предоплаченные кредиты** | пакет токенов/запросов со скидкой заранее: снижает отток, улучшает cash flow; обязателен дашборд burn rate |
| **Enterprise / кастом** | скидка за объём + SLA + dedicated instances, договорная цена; **обязательны верхний порог лимитов и overages policy**, чтобы клиент не получил неожиданный счёт |

### От внутреннего сервиса к публичному API: четыре стадии

```
Internal  →  Dev Preview  →  Paid Beta  →  Public API
```

| Стадия | Что есть |
|---|---|
| **Internal** | только внутренние команды; нет SLA и документации; быстрая итерация, прямая связь с пользователями |
| **Dev Preview** | закрытый доступ для партнёров; первая документация, базовый SDK; сбор обратной связи |
| **Paid Beta** | API Gateway, rate limiting, биллинг; онбординг через Developer Portal; первые реальные клиенты |
| **Public API** | открытая регистрация, полная документация, SLA и support SLA, маркетинг и экосистема |

### Метрики успеха API-продукта

| Метрика | Смысл | Ориентир |
|---|---|---|
| 📈 **Adoption rate** | сколько команд/клиентов реально используют API | рост month-over-month |
| ⚡ **Time to First Call** | от регистрации до первого успешного запроса | **< 30 минут** |
| 🛡 **API reliability** | uptime + p99 latency | SLA для внешних 99,9 %+ |
| 💰 **Revenue / usage** | выручка, активные платящие клиенты | — |

## Разбор кейсов: Enterprise против SMB

Два AI-сервиса, спроектированных под разных потребителей — самая содержательная часть лекции.

| Критерий | **Enterprise B2B: база знаний** | **SMB: чат-бот техподдержки** |
|---|---|---|
| **Потребитель** | крупный бизнес, встраивает API в юридическую систему; высокий compliance | малый/средний бизнес, автоматизирует ответы техподдержки, подключает к Zendesk |
| **Ценность** | «сократите ревью договора с 2 часов до 4 минут»; данные не покидают страну | минимальный time-to-market, подключение по инструкции из N шагов |
| **Протокол** | REST + **async job queue**: `POST /v1/documents/analyze` → `job_id`, `GET /v1/jobs/{id}/status`, webhook по готовности (30–90 с) | REST + **SSE-стриминг**: `POST /v1/reply/suggest`, `POST /v1/reply/stream` — токены по мере генерации |
| **Auth** | OAuth 2.0 client credentials → short-lived token (TTL 1 ч) с `tenant_id` и scopes | API-ключи `X-API-Key: sk-...` |
| **Rate limiting** | по `tenant_id` и контракту (500 документов/сутки, max 10 concurrent jobs); 429 + уведомление аккаунт-менеджеру | по ключу и тарифу (Free 100/сутки, Pro 50 000/мес); **429 + ссылка на upgrade в теле ответа как конверсионный механизм**; burst 10 req/s |
| **Тенантность** | dedicated inference-нода, audit log (`GET /v1/audit/logs`) | pool-изоляция, ключ видит только свою историю |
| **Версионирование** | deprecation **12 месяцев**, RFC перед каждым breaking change, отдельный staging | deprecation **30 дней**, поддержка старой версии ~3 месяца; новые поля в ответе не считаются breaking |
| **Документация** | OpenAPI со всеми edge cases, security guide, compliance-документы | quickstart на 5 шагов («скопируй curl — получи ответ за 2 минуты»), готовые плагины Zendesk/Freshdesk, видео на 3 минуты |
| **Онбординг** | 2–4 недели, звонок с Solutions Engineer, sandbox | self-serve, **Time to First Call < 10 минут** |
| **Монетизация** | Annual Contract Value + overage за документы сверх лимита — **корпоративный CFO хочет предсказуемый бюджет** | Freemium + тарифы (Free 500 ответов/мес, Starter, Pro со стримингом и приоритетом) |
| **Ключевой KPI** | продление контракта, соблюдение SLA | конверсия Free → Paid, отсутствие оттока |

**Три вывода лекции по кейсам:**

1. **Потребитель определяет всё** — протокол, документацию, монетизацию, уровень изоляции. Не проектируйте API до ответа на вопрос «кто мой потребитель и что для него провал?».
2. **Enterprise и SMB — принципиально разные продукты.** Один API для обоих сегментов будет неудобен для всех.
3. **AI-специфика влияет по-разному:** Enterprise критична стабильность модели и async-обработка; SMB — стриминг и низкая стоимость запроса.

Отдельно разобрано сравнение **OpenAI API** (2020, pay-per-token, сильный Developer Portal и Playground, экосистема plugins/fine-tuning, rate limits по уровням) и **Claude API** (2023, упор на safety и long-context, tier-based rate limits, фокус на enterprise-безопасность, Developer Console).

## Ключевые тезисы занятия (со слайда)

1. **API — это продукт.** Проектируйте с точки зрения потребителя, а не технической реализации.
2. Определите тип потребителя заранее — у каждого свои требования.
3. **Design-First:** сначала контракт (OpenAPI), потом код.
4. **Версионирование с самого старта**, URI-схема `/v1/`, `/v2/` — простой и проверенный подход.
5. **Документация живёт как часть продукта:** OpenAPI + живые примеры + changelog обязательны для публичных API.
6. **Закладывайте API Gateway:** контроль доступа + rate limiting + мониторинг.

## Вопросы и ответы

1. **Политика стабильности моделей на практике.** Обновление модели меняет поведение при неизменном контракте. Как это оформляют: версия модели в имени (`model=zubr-1.5`) с гарантией неизменности N месяцев, или «latest»-алиас плюс закреплённые снапшоты, как у OpenAI?
2. **Оценка стоимости до отправки запроса.** Слайд требует дать клиенту возможность посчитать цену заранее. Для input это токенизация на клиенте, а как быть с output, который заранее неизвестен — только через `max_tokens` как верхнюю границу?
3. **Async vs streaming для одного и того же сценария.** В кейсах Enterprise получил job queue, SMB — SSE. Что делать, когда один потребитель хочет и то, и другое (интерактивный режим и пакетная обработка): два эндпоинта или один с параметром?
4. **429 как конверсионный механизм.** Ссылка на upgrade в теле 429 — приём продуктовый, но он же ухудшает DX. Есть ли данные, что это не отталкивает разработчиков, и где граница между «подсказкой» и «навязыванием»?
5. **Deprecation 12 месяцев и стоимость поддержки.** Год параллельной поддержки двух версий AI API означает и две версии модели в памяти GPU. Как это закладывается в цену Enterprise-контракта?

2. **Совместимость с OpenAI API — наше главное продуктовое решение, и оно уже принято.** Лекция называет это отраслевым стандартом: клиент подключается сменой `base_url`, Time to First Call падает до минут, экосистема SDK достаётся бесплатно. Стоит зафиксировать это отдельным ADR как осознанный выбор, а не «так получилось», — с оборотной стороной: мы наследуем чужой контракт и обязаны за ним следовать.
3. **Политика стабильности моделей — наша реальная дыра.** Алиас `zubr` в LiteLLM сейчас указывает на зеркало qwen3.6-35b, при этом на сайте платформы обещаны ответы по 25 кодексам, а дообученная [Zubr1.5-VL-32B](https://huggingface.co/ArtCloud/Zubr1.5-VL-32B) в шлюзе ещё не заведена ([[zubr-vl-32b-model]]). По уроку это классическая ошибка AI API: **поведение под клиентом может смениться при неизменном контракте**. Нужны версионированные имена моделей (`zubr-1.5`) с гарантией неизменности и алиас `latest` отдельно.
4. **Два сегмента — два продукта, и у нас они уже смешаны.** Банк-клиент (МТБанк) — это Enterprise-профиль: SLA, аудит-лог, dedicated inference, длинный deprecation. Розничные пользователи консоли — SMB-профиль: self-serve, freemium, стриминг. Сейчас их обслуживает один контур с одинаковыми правилами; из таблицы кейсов видно, что расходиться надо по tenant-тарифам, а не по инстансам.
5. **429 с подсказкой апгрейда — дешёвая продуктовая правка.** У нас rate limiting уже есть в LiteLLM; добавить в тело ответа причину и ссылку на смену тарифа — работа на час, а это прямой конверсионный механизм. Тот же ответ должен возвращать текущий расход — требование «показывать расход в реальном времени» из раздела монетизации.
6. **Урок закрывает круг блока 6.** FinOps (28) считал себестоимость, governance (30) — ответственность, этот урок — как то и другое превращается в цену и контракт для клиента. Для защиты финального проекта это готовая рамка: платформа описывается не только как архитектура, но и как продукт с потребителями, стадией зрелости и метриками (Time to First Call, adoption, uptime).
