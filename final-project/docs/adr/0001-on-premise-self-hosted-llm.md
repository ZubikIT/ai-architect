# ADR-0001. Self-hosted open-weight LLM вместо облачного API (on-premise / air-gapped)

## Контекст
Проектируем ядро корпоративной интеллектуальной системы. Это не «нам нужна LLM», а набор **ограничений**:

- **ТЗ:** система работает **полностью автономно (on-premise / air-gapped)**, без доступа к внешним API (OpenAI / Anthropic).
- **Безопасность и право:** база знаний — внутренние документы и регламенты, потенциально содержащие ПДн и коммерческую/банковскую тайну. По **152-ФЗ** и требованиям ИБ данные **не должны покидать контур** организации.
- **Железо:** on-prem сервер **Lenovo ThinkSystem SR675 V3 с 2× NVIDIA H100 80 GB** (фиксированный ресурс в контуре, не облако). Sizing и квантование — отдельный [ADR-0006](0006-kvantovanie-i-sizing-gpu.md).
- **Команда:** есть DevOps, ML-компетенции — начальные.
- **Санкционный риск:** доступ к зарубежным SaaS-LLM из РФ нестабилен (оплата, блокировки).

## Рассмотренные варианты
1. **SaaS LLM API** (OpenAI / Anthropic / Azure OpenAI)
   - **Хорошо:** эталонное качество, Time-to-Market < 1 недели, ноль инфраструктуры, OpEx без капзатрат.
   - **Плохо:** данные покидают периметр — **прямое нарушение ТЗ и 152-ФЗ**; не работает в air-gapped; vendor lock-in; OpEx растёт с нагрузкой; санкционные/платёжные риски.
2. **Self-hosted open-weight LLM** (Qwen 2.5/3, DeepSeek, T-lite / Saiga) на vLLM/SGLang/TGI с квантованием
   - **Хорошо:** данные остаются в контуре; полный контроль над инференсом; работает air-gapped; нет лицензионных платежей; есть модели с поддержкой русского.
   - **Плохо:** качество ниже топовых SaaS (риск галлюцинаций на сложных запросах); нужен MLOps и GPU (CapEx); ответственность за обновления и безопасность модели — на нас.
3. **Гибрид** (роутинг: простые запросы — локально, сложные — в облако)
   - **Хорошо:** баланс качества и стоимости.
   - **Плохо:** часть данных всё равно уходит наружу → **нарушает air-gapped**, усложняет контроль PII и аудит. Не проходит по ТЗ.

## Решение
Используем **self-hosted open-weight LLM**, развёрнутую внутри изолированного контура; внешние LLM-API **запрещены**. Вариант 1 (SaaS) — **Rejected** (blocker по безопасности и прямое нарушение ТЗ), вариант 3 (гибрид) — **Rejected** (нарушает air-gapped).

Конкретная модель, движок инференса и стратегия квантования выносятся в отдельные решения (см. «Связи»), чтобы это фундаментальное ADR оставалось стабильным при их эволюции.

## Последствия
- **Положительные:**
  - Соответствие ТЗ (air-gapped) и 152-ФЗ; данные не покидают контур.
  - Нет переменных расходов на токены (CapEx вместо OpEx), предсказуемый TCO.
  - Независимость от внешних провайдеров и санкционных рисков.
- **Отрицательные / риски:**
  - Качество ответов ниже моделей класса GPT-4 → риск неверных ответов на сложных запросах (митигируется RAG-grounding + guardrails).
  - Нужны GPU и компетенции DevOps/MLOps (мониторинг, обновления, безопасность весов).
  - Throughput и длина контекста ограничены доступным железом.
- **Что придётся изменить дальше:**
  - Выбрать модель (RU-поддержка, размер, лицензия), движок инференса, стратегию квантования и sizing GPU.
  - Внедрить Input/Output Guardrails (PII, prompt injection, toxicity) и Model Card на выбранную модель.

## Compliance & Ethics _(AI-специфичный раздел, урок 08)_
- **152-ФЗ / тайна:** инференс и данные — только в контуре; внешний трафик к LLM-провайдерам заблокирован на сетевом уровне.
- **Галлюцинации:** обязательный RAG-grounding, ответ «не знаю» как валидный, дисклеймер «я бот, могу ошибаться».
- **Bias:** базовая instruction-tuned модель → риск предвзятости; план — eval на golden set (RAGAS) перед релизом.
- **Jailbreak / toxicity:** output-guardrails как постфильтр перед отдачей пользователю.
