# ADR-0016. ACL на уровне узлов графа и чанков — материализованные метки + предикат в каждом запросе

## Контекст

ТЗ (занятие [32](../../sessions/32-vybor-temy.md)) относит разграничение доступа к разряду **критичных** критериев: *«Security: проверка прав доступа работает — User B не получает ответ по секретному документу»*, а Security-by-Design формулируется именно как разграничение **на уровне чанков / узлов графа**, а не приложения.

Силы давления:

- **Два хранилища знаний.** После [ADR-0012](0012-graph-db.md) доступ к знанию идёт двумя путями: payload-фильтр Qdrant ([ADR-0004](0004-vector-db.md)) и обход графа в Neo4j. **Дыра в любом из них обнуляет оба** — режим доступа обязан быть единым.
- **Утечка через структуру.** В графе закрытый документ выдаёт себя рёбрами: даже не показывая текст, обход сообщает о существовании, названии и связях. Значит фильтр обязан работать **на каждом узле пути**, а не на финальной выдаче.
- **Neo4j Community не имеет ролевой модели БД** ([ADR-0012](0012-graph-db.md)) — fine-grained RBAC только в Enterprise. Обеспечивать доступ средствами самой БД нельзя.
- **Источник прав.** В реальном контуре права уже живут в Keycloak (группы) и наследуются из источников — SharePoint/Confluence через permission-aware коннекторы Onyx ([ADR-0008](0008-knowledge-base-connectors.md)). Своя параллельная модель прав недопустима: она разъедется с оригиналом.
- **Урок 26 (multi-tenancy):** контекст субъекта берётся **из проверенного токена, а не из тела запроса**. Текущий [ADR-0011](0011-sufler-pipeline-integration.md) берёт роли из `body.user.groups` пайплайна Open WebUI — это доверие к телу запроса, то есть потенциальная подмена роли (Spoofing из STRIDE-таблицы [методики занятия 33](../../sessions/33-konsultaciya.md)).
- **Latency.** Проверка прав лежит на горячем пути retrieval, который вызывается многократно внутри агентного цикла → внешний вызов PDP на каждый узел неприемлем.
- **№ 99-З:** доступ к ПДн и служебной тайне подлежит аудиту; отказ должен логироваться так же, как выдача.

## Рассмотренные варианты

1. **Post-filtering: retrieval без прав, отсев перед ответом**
   - **Хорошо:** тривиально реализуется.
   - **Плохо:** закрытые чанки вытесняют разрешённые из top-k (пользователь получает пустоту вместо доступного ответа); утечка через структуру графа и через тайминг; ответ уже побывал в контексте LLM. **Rejected.**
2. **Материализованный ACL на узле/чанке + предикат в каждом запросе (pre-filtering)** _(выбран)_
   - На чанке и документе хранится денормализованный список допущенных ролей `acl_roles`; тот же список — в payload Qdrant. Каждый Cypher-обход и каждый векторный поиск несут обязательный предикат по ролям субъекта.
   - **Хорошо:** одинаковая семантика в обеих БД; фильтр внутри обхода (нет утечки через связи); нулевые внешние вызовы на горячем пути; работает на Neo4j Community.
   - **Плохо:** денормализация → нужна пересинхронизация при изменении прав в источнике; выразительность ограничена ролями (сложные ABAC-правила не покрываются).
3. **Внешний PDP (OPA / Cedar) с запросом решения по каждому узлу**
   - **Хорошо:** богатые ABAC-политики, правила отделены от данных.
   - **Плохо:** сетевой вызов на каждый узел обхода — прямое нарушение бюджета latency; ещё один критичный компонент в air-gapped. **Отклонён для горячего пути**, но оставлен как место для сложных политик на этапе ingestion (какие роли материализовать).
4. **Neo4j Enterprise fine-grained RBAC**
   - **Хорошо:** доступ обеспечивает сама БД.
   - **Плохо:** платная лицензия, чего проект не предполагает; и всё равно не покрывает Qdrant → единый режим не достигается.
5. **Silo: отдельная БД/коллекция на подразделение (урок 26)**
   - **Хорошо:** физическая изоляция — самая надёжная.
   - **Плохо:** ломает главную ценность графа — межведомственные связи ЛПА (один приказ касается нескольких подразделений); кратный рост инфраструктуры. Модель **Pool с материализованными метками** (Bridge-элементы) адекватнее.

## Решение

**Вариант 2** — единая материализованная модель доступа поверх обоих хранилищ, с контекстом субъекта **из проверенного JWT**.

**Поток авторизации:**

```
Keycloak (группы) → access token (JWT)
  → RAG/агент-сервис ВАЛИДИРУЕТ подпись по JWKS Keycloak (кэш ключей, TTL)
  → roles := claims.groups   (body.user — только для UX и логов, НЕ для доступа)
  → RequestContext {subject, roles, request_id} создаётся ОДИН раз на запрос
  → передаётся в слой репозитория; агенты контекст не конструируют и не изменяют
```

**Правила, которые фиксируем как архитектурные инварианты:**

1. **Deny-by-default.** Узел/чанк без метки `acl_roles` недоступен никому, кроме служебной роли индексатора. Отсутствие данных о правах — не «разрешено».
2. **Предикат на каждом узле пути.** В обходе графа условие по ролям применяется к каждому узлу, а не к стартовому: путь через закрытый узел не существует для непривилегированного субъекта.
3. **Единственная точка построения запросов.** Cypher и запросы Qdrant собираются только в слое репозитория, принимающем `RequestContext` обязательным аргументом; у агентов нет доступа к драйверу БД. «Забыть фильтр» можно ровно в одном месте, и оно покрыто тестами.
4. **Права агента ⊆ прав пользователя.** Цифровой сотрудник («кадровик», «юрист») работает под контекстом вызвавшего пользователя, а собственная роль агента может только **сузить** доступ (least privilege, ASI03). Агент не является субъектом с собственными привилегиями.
5. **Учётки БД разделены:** ingestion пишет под учёткой с правом записи, runtime-запросы идут под read-only учёткой.
6. **Аудит симметричен:** и выдача, и отказ пишутся в журнал (`subject`, `request_id`, `doc_id`, решение) — иначе отказ невозможно расследовать.

**Синхронизация прав:** источник истины — Keycloak и права оригинальных документов (Onyx permission-aware). Ingestion материализует их в `acl_roles` при индексации; инкрементальная пересинхронизация — по расписанию и по событию изменения прав; членство субъекта в группах кэшируется с коротким TTL, чтобы отзыв прав вступал в силу без рестарта. **Известное ограничение:** между отзывом права в источнике и пересинхронизацией существует окно — фиксируем его явно и сокращаем приоритетной обработкой событий отзыва.

**Проверка (обязательный тест ТЗ):** негативный автотест «User B» в CI — пользователь без роли задаёт вопрос, ответ на который содержится только в закрытом документе. Проверяется, что (а) ответ не содержит защищённого текста, (б) чанк не попал в контекст LLM (по трейсу, а не по финальной строке), (в) не раскрыт факт существования документа, (г) отказ зафиксирован в аудите. Тест выполняется и для векторного пути, и для графового обхода, и для вызова инструментов агента.

## Последствия

- **Положительные:**
  - Критичный критерий ТЗ закрывается проверяемым механизмом и демонстрируется в видео-демо одним кадром (тот же вопрос от User A и User B).
  - Единая семантика прав для Qdrant и Neo4j — нет «второй двери».
  - Нулевой сетевой overhead авторизации на горячем пути.
  - Закрывается Spoofing-риск текущего `body.user` из [ADR-0011](0011-sufler-pipeline-integration.md).
- **Отрицательные / риски:**
  - **Денормализация прав** → окно рассинхронизации при отзыве доступа (митигация выше); при массовом изменении прав нужна переиндексация меток.
  - Ролевая модель не покрывает сложный ABAC (например, «доступ только в рабочее время из офисной сети») — при появлении таких требований подключать PDP на этапе материализации.
  - Рост payload/свойств узлов при большом числе ролей на документ → индекс по `acl_roles`, при необходимости — нормализация в роли-группы.
  - Появляется жёсткая зависимость от корректности `RequestContext` — компенсируется тем, что он один и покрыт тестами.
- **Что придётся изменить дальше:**
  - [ADR-0011](0011-sufler-pipeline-integration.md) перевести на валидацию JWT вместо `body.user.groups` (обновить статус/редакцию ADR).
  - ER-диаграмма: `acl_roles` на CHUNK и на узлах графа, журнал отказов в AUDIT_LOG.
  - `/backend`: `RequestContext`, слой репозитория, негативные тесты; `/infra`: JWKS-эндпоинт Keycloak доступен сервису в контуре.

## Compliance & Ethics _(AI-специфичный раздел, урок 08)_

- **№ 99-З:** доступ к ПДн ограничен ролями на уровне данных; журнал выдач и отказов — доказательная база для НЦЗПД; право на забвение исполняется удалением чанка, узла и вектора по общему `chunk_id`.
- **Минимизация:** агент видит ровно тот срез знаний, что и пользователь — исключён сценарий «ИИ знает больше, чем позволено спрашивающему».
- **Прозрачность отказа:** пользователю сообщается, что материал существует вне его доступа, **только если сам факт существования не является защищаемым**; иначе ответ — «не найдено». Правило фиксируется продуктово, а не отдаётся на усмотрение модели.
- **Аудируемость:** каждое решение о доступе привязано к `request_id`, что делает разбор инцидента возможным (Repudiation из STRIDE).
