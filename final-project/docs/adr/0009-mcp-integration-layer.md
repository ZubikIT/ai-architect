# ADR-0009. MCP как стандартный слой интеграции с внешними системами

## Контекст
Агентам и UI нужна **точка входа интеграции** с внешними системами: не только читать БЗ (это ADR-0008), но и **выполнять действия** (создать задачу в Jira, дёрнуть внутренний API, запрос в БД и т.п.). Силы давления:

- **Не плодить кастом под каждый фронт:** две плоскости (Open WebUI — персонально, Onyx — совместно) + LangGraph-агенты (ADR-0005) → интеграции хочется писать **один раз**, а не отдельно под каждую систему.
- **Air-gapped (ADR-0001):** интеграции и их серверы — в контуре.
- **Безопасность:** инструмент = доступ к действиям → нужны least-privilege, scoping, аудит.
- **Стек:** Qwen3.6 с tool-calling (ADR-0002); Open WebUI (ADR-0007) и Onyx (ADR-0008) — обе нативно поддерживают MCP.

## Рассмотренные варианты
1. **MCP (Model Context Protocol)** _(выбран)_
   - **Хорошо:** единый стандарт инструментов; **обе системы поддерживают нативно** — Open WebUI как MCP-клиент (v0.6.31+, «MCP / Streamable HTTP», + прокси **mcpo** для MCP↔OpenAPI), Onyx как **клиент И сервер** (MCP Actions: выбор подмножества инструментов, auth none/API-key/OAuth). Декаплинг интеграций от UI; переиспользование; LangGraph-агенты тоже могут вызывать MCP-инструменты. Бонус: **Onyx как MCP-сервер** → агенты (LangGraph / Open WebUI) запрашивают общую БЗ через стандартный интерфейс.
   - **Плохо:** спецификация MCP ещё развивается (RC 2026-07-28) → пинить версии; MCP-сервер = мощный доступ → поверхность атаки, нужен security-review.
2. **Кастом per-system** (Open WebUI Pipelines/OpenAPI-tools + Onyx Actions раздельно)
   - **Плохо:** дублирование интеграций на каждый фронт; рассинхрон.
3. **Только OpenAPI tool servers** (оба поддерживают)
   - **Хорошо:** простой REST.
   - **Плохо:** MCP богаче (tools/resources/prompts) и нативно поддержан; mcpo всё равно мостит MCP↔OpenAPI, так что MCP не дороже.

## Решение
**MCP — стандартный слой интеграции.** Внутренние системы оборачиваем в **MCP-серверы** (в контуре) один раз → их потребляют **обе плоскости**: Open WebUI (персонально/агенты) и Onyx (совместно/агенты), а также LangGraph (ADR-0005). Дополнительно **Onyx поднимаем как MCP-сервер** — общая БЗ становится инструментом для агентов. Auth — least-privilege (API-key / OAuth), админ выбирает подмножество инструментов на систему.

**Статус `proposed`:** до `accepted` — PoC (один MCP-сервер, подключённый к Open WebUI и Onyx) + security-review и политика auth/scoping. Зафиксировать **реестр MCP-серверов** (что оборачиваем).

## Последствия
- **Положительные:**
  - Один интеграционный стандарт на обе плоскости и агентов → пишем интеграцию один раз.
  - Onyx-as-MCP-server даёт агентам доступ к общей БЗ через стандартный интерфейс.
  - Декаплинг: смена UI не ломает интеграции.
- **Отрицательные / риски:**
  - MCP-серверы — **поверхность атаки** (выполняют действия) → scoping, auth, аудит вызовов, security-review; размещение в контуре/DMZ по чувствительности.
  - Спецификация MCP развивается → пинить версии, следить за breaking changes.
  - Ops: поддержка и мониторинг набора MCP-серверов.
- **Что придётся изменить дальше:**
  - Реестр MCP-серверов и матрица доступа (какой фронт/агент к каким инструментам).
  - HITL на необратимые действия (ADR-0005); аудит-трейл вызовов инструментов.

## Compliance & Ethics _(AI-специфичный раздел, урок 08)_
- **Air-gapped / № 99-З:** MCP-серверы — в контуре; least-privilege и аудит вызовов; никаких внешних MCP-эндпоинтов.
- **HITL:** необратимые/опасные действия (запись, удаление, отправка) — только после подтверждения человеком.
- **Scoping:** Onyx позволяет админу ограничить набор инструментов для агентов — использовать для минимизации прав.
