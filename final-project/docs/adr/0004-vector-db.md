# ADR-0004. Vector Database — Qdrant (vs Milvus, Weaviate)

## Контекст
RAG-ядру (уроки 06/08) нужно self-hosted хранилище векторов для базы знаний. Силы давления:

- **Air-gapped / № 99-З (ADR-0001):** строго self-hosted, офлайн, данные в контуре.
- **Гибридный поиск (урок 06):** dense + sparse (BM25) с объединением — лечит «слепые зоны» dense-поиска (точные термины, артикулы, аббревиатуры).
- **Metadata filtering / RBAC:** pre-filtering по метаданным («мои документы», уровень доступа) — чтобы вектор не находил чужое (урок 06; ER-диаграмма с RBAC из брифа).
- **Эксплуатация:** команда с начальным ML → ценится **низкий операционный overhead** (мало внешних зависимостей).
- **Масштаб:** корпоративная база документов (порядок 10^5–10^7 чанков) — _точный профиль уточнить (открытый вопрос брифа)._
- **Совместимость:** интеграция с оркестратором (LangGraph) и Open WebUI (ADR-0007).

## Рассмотренные варианты
1. **Qdrant** _(выбран)_
   - **Хорошо:** простой self-host (один сервис, Docker, без тяжёлых зависимостей); first-class **payload-фильтрация** (RBAC pre-filtering); нативный **hybrid (dense + sparse)**; Apache 2.0; офлайн; быстрый (Rust); комфортно держит 10^7 векторов на нашем железе; **уже используется в моём кейсе Суфлёр** (знакомый инструмент → ниже риск).
   - **Плохо:** на экстремальном масштабе (миллиарды векторов) уступает распределённому Milvus — для нас не актуально.
2. **Milvus**
   - **Хорошо:** топовая масштабируемость (миллиарды векторов), распределённость, GPU-индексы.
   - **Плохо:** тяжёлый ops-footprint (etcd + объектное хранилище + брокер) → **избыточен** для корпоративной БЗ и рискован для команды с начальным ML.
3. **Weaviate**
   - **Хорошо:** богатый функционал, встроенный hybrid, модульность, GraphQL.
   - **Плохо:** тяжелее и «модульнее» нужного; модель развёртывания сложнее Qdrant без явной выгоды для нашего сценария.

## Решение
Берём **Qdrant** как Vector DB. Что перевесило: минимальный операционный overhead под air-gapped и команду с начальным ML, first-class payload-фильтрация под RBAC, нативный hybrid (dense+sparse) под требование урока 06, Apache 2.0, достаточный масштаб на нашем железе и уже наработанная экспертиза. **Milvus** — **Rejected** (ops-overkill для нашего масштаба), **Weaviate** — отклонён как «тяжелее без выгоды».

**Статус `proposed`:** перед `accepted` подтвердить профиль нагрузки (число чанков, RPS, размер вектора эмбеддера) — если он выйдет в миллиарды векторов, пересмотреть в пользу Milvus (`superseded by`).

## Последствия
- **Положительные:**
  - Лёгкий self-host в контуре; быстрый старт, мало движущихся частей.
  - Payload-фильтрация закрывает RBAC pre-filtering и multi-tenancy без костылей.
  - Нативный hybrid → реализуем рекомендацию урока 06 (BM25 + вектор) внутри одной БД.
- **Отрицательные / риски:**
  - Не рассчитан на миллиарды векторов — митигируется проверкой профиля нагрузки.
  - Бэкапы/реплинг и HA Qdrant настраиваем сами (регламент снапшотов в контуре).
- **Что придётся изменить дальше:**
  - Зафиксировать схему коллекций, payload-поля под RBAC и конфиг sparse-вектора (ER-диаграмма).
  - Согласовать размерность вектора с выбором эмбеддера (отдельное решение по embedding-модели).

## Compliance & Ethics _(AI-специфичный раздел, урок 08)_
- **№ 99-З / air-gapped:** Qdrant self-hosted в контуре, без внешних обращений; снапшоты — внутри периметра.
- **RBAC:** payload-фильтры обеспечивают, что пользователь видит только разрешённые документы (учёт доступа к ПДн).
- **Удаление/ретеншн:** поддержать удаление векторов по запросу (право на забвение / ретеншн-политики).
