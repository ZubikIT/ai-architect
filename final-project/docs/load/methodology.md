# Методика нагрузочного замера

> Приложение к [нагрузочному отчёту](../load-report.md). Вынесено отдельно, чтобы отчёт читался с цифр, а спорить можно было с методикой.

## Что именно измеряется

Замер покрывает **синхронный путь без генерации**: HTTP → guardrails → эмбеддинг запроса → гибридный поиск (Qdrant + BM25) → обход графа в Neo4j → rerank → сборка ответа с цитатами. Стенд без GPU, поэтому `SUFLER_USE_LLM=0`: ответ собирается экстрактивно.

**Это не «половина отчёта», а его осмысленная часть.** Генерация на 2× H100 сосчитана отдельно и другим методом — [ADR-0006](../adr/0006-kvantovanie-i-sizing-gpu.md) (sizing VRAM и параллелизма) и [ДЗ-17](../../../17-optimizaciya-inferensa-llm/Zubik_DZ-17_sizing-inference.md) (пропускная способность движка). Мерить её на CPU-стенде бессмысленно: цифра не перенесётся. А вот стоимость retrieval-части от GPU не зависит вовсе — и именно она определяет, сколько запросов вообще дойдёт до модели.

Прямо не измерено, и это названо здесь, а не спрятано в примечании: TTFT, токены/с, стоимость запроса, поведение под смешанным профилем трафика (классы A/B/C из [ДЗ-24](../../../24-high-load-low-latency/Zubik_DZ-24_highload-realtime.md)), кэш (в MVP его нет).

## Закрытая петля, а не фиксированный поток

`N` виртуальных клиентов шлют запрос, дожидаются ответа и сразу шлют следующий; `N` растёт ступенями 1 → 2 → 4 → 8 → 16.

Открытая петля (фиксированный arrival rate) моделирует реальный трафик точнее, но выше точки насыщения вырождается: очередь растёт неограниченно, и замер показывает уже не сервис, а терпение генератора. Закрытая петля отвечает на вопрос, ради которого отчёт и делается, — **где RPS перестаёт расти и почему**.

Следствие, которое обязано быть названо вслух: закрытая петля даёт латентность **при `N` одновременных клиентах**, а не «при нагрузке X RPS». Для проверки SLO этого достаточно; для capacity planning под заданный поток — нет, там нужен открытый профиль с backpressure.

## Сценарии

| Сценарий | Эндпоинт | Что нагружает |
|---|---|---|
| `healthz` | `GET /healthz` | база отсчёта: ASGI, middleware, экспорт метрик. Без неё непонятно, что из латентности принадлежит пайплайну, а что — обвязке |
| `ask` | `POST /ask` | одиночный GraphRAG: эмбеддинг → гибридный поиск → обход графа → сборка |
| `ask-acl` | `POST /ask`, роль `legal` | тот же путь, но субъекту доступно больше документов. Сценарий задумывался как проверка «ACL не влияет на стоимость» — замер показал обратное, и это стало одним из выводов отчёта |
| `agents` | `POST /agents/ask` | мультиагентный путь: веер из двух ролей, то есть **два прохода retrieval** на один запрос |

## Правила замера

1. **Прогрев отбрасывается** — 5 с на каждую ступень, тем же сценарием и тем же параллелизмом. Первые запросы прогревают пулы соединений и аллокатор; их включение завышает хвосты на порядок.
2. **Ступень — 30 с.** Компромисс: короче — совсем мало точек, длиннее — прогон перестаёт помещаться в итерацию. Ступень фиксирована по времени, а не по числу запросов, поэтому медленные сценарии дают меньшую выборку (18–64 замера) — и **p99 на такой выборке недостоверен**. Это названо в отчёте, а не замаскировано округлением.
3. **Перцентили по ближайшему рангу**, без интерполяции: на сотнях замеров интерполяция создаёт видимость точности, которой в данных нет.
4. **Ошибки считаются отдельно** и разбиты по коду ответа и типу исключения. Неуспешный запрос не попадает в выборку латентности — иначе быстрый отказ улучшает перцентили.
5. **Один прогон — один отчёт.** Цифры ниже получены за один сеанс на неизменной конфигурации; сравнивать их с другими прогонами можно только вместе с версией стека.

## Ограничения стенда

- **Генератор нагрузки живёт на том же хосте**, что и сервис со всеми БД. Выше некоторого параллелизма они конкурируют за те же ядра, и это видно в данных. Разнести было нечем: другого хоста в контуре стенда нет.
- **Виртуальный CPU без GPU**, эмбеддер и реранкер — лёгкие CPU-модели вместо целевых. Абсолютные цифры латентности к прод-конфигурации не переносятся; переносятся **соотношения между шагами** и точка насыщения по архитектурной причине.
- **Это ограничение снято для реранка** в [повторном замере](../load-report.md#реранк-вынесен-на-сервис-платформы--повторный-замер): он идёт на целевой модели `bge-reranker-v2-m3` сервисом платформы, а не суррогатом на CPU. Там же контрольный прогон старой конфигурации на том же стенде, поэтому две конфигурации сравнимы между собой напрямую. Эмбеддер по-прежнему суррогат.
- **Демо-корпус: 4 документа, 19 чанков.** Поиск по такому индексу быстрее прод-объёма, но узкое место от размера индекса почти не зависит — оно определяется длиной запроса и числом кандидатов на реранк. После переноса реранка на сервис зависимость от числа кандидатов ослабла: сервис батчит их в одном запросе, и разрыв между широкими и узкими правами сжался с ×1,49 до ×1,37.
- **Один воркер uvicorn**, без лимитов CPU и памяти на контейнере. Это сознательно оставлено как есть: отчёт должен показать поведение той конфигурации, которая лежит в репозитории, а не подкрученной под замер.

## Воспроизведение

```bash
cd final-project/infra && docker compose --profile core --profile obs up -d
cd ../backend
python -m tools.loadtest \
  --scenarios healthz ask ask-acl agents \
  --concurrency 1 2 4 8 16 \
  --duration 30 --warmup 5 \
  --out ../docs/load/raw.json
```

Сырые замеры — [`raw.json`](raw.json), инструмент — [`tools/loadtest.py`](../../backend/tools/loadtest.py).
